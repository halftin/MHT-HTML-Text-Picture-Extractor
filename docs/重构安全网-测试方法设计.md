# 重构安全网 — 测试方法设计

> 日期：2026-09-26
> 用途：为「架构重构 + GUI/控制/业务三层解耦」提供**每一步可复跑**的全量验证手段
> 前置：`docs/全量功能清单.md`、`docs/全量链路清单.md`（会话 17 盘点产出）

---

## 一、现状盘点（重构前的既有安全网）

| 层次 | 规模 | 特点 | 局限 |
|---|---|---|---|
| **单元测试** | **304 测试 / 24 类** | `util`（DropResolver 32、GroupStructure 23、ParamScope 26、OutputUnitPlanner 20…）与 `processor`（ImageBatchProcessor 27）覆盖良好；全部纯逻辑、零 JavaFX | 不覆盖 GUI 交互；`gui` 包**零直接单测** |
| **GUI 自动化** | **30 项断言**（`runAutomatedTests`，`:5407–6053`） | 驱动真实应用：模式切换、参数弹窗、增量导入、撤销链、分组重命名、拖拽（排序/跨组/合并）、参数三级覆盖、清除参数、进度条配色、输出单元规划、文本/图片预览、**缓存生命周期 C1/C2/C3/C7/C8**、locale 持久化 | 断言的是**控件状态与内部状态**，不校验**落盘产物内容**；断言文案耦合中文（i18n 后已用 key 渲染） |
| **手工验收** | 零散 | 模态弹窗（关窗清空、10GiB 提醒、大文件确认） | 不可自动复跑 |

**结论**：既有安全网**比预期强**（304 + 30），但缺两块：
- **① 端到端产物校验**：没有任何测试验证"提取出的文件/归档内容是否正确"
- **② 无头驱动 API**：所有功能只能通过 GUI 控件触发，重构中 GUI 一改，测试就跟着碎

## 二、缺口分析：为什么重构需要额外两层

重构要动的是 `MainController`（6100 行，165 方法）与三层解耦。既有测试的问题：

1. **30 项 GUI 断言写在 `MainController` 里**（`runAutomatedTests`）—— 这是 `项目需求文档.md` §四 A-2 记录的「自锁效应」：
   一要拆 `MainController`，这些断言就跟着碎，反而抬高重构成本
2. **只验控件状态，不验产物**：重构很可能保持控件状态正确、却改变落盘结果（如命名、字节、归档结构）
3. **无层级验证**：无法回答"业务层是否已真正脱离 GUI"

因此补两层：**产物黄金基线** + **无头驱动 API**。

## 三、Layer A：端到端产物黄金基线（重构前先建）

### 3.1 目标

对**每一类产物**建立"输入夹具 → 期望输出"的字节级基线，重构前后必须完全一致。

### 3.2 为什么这是最有力的手段

本项目已用过这个手段且**证明了它的价值**：会话 10 的 **C5 验证**
（同批 MHT 跑两次提取，`git diff --no-index` 递归比对两输出目录，4 文件 SHA 全同）
当场证明了"缓存复用无字节偏差"。把它**系统化、扩到所有产物类型**，即是本方案。

### 3.3 夹具集（fixtures）

需在 `src/test/resources/fixtures/` 建一套**覆盖全部特性组合**的 MHT：

| 夹具 | 覆盖点 |
|---|---|
| `simple-text.mht` | 纯文本 HTML，无图片 |
| `single-image.mht` | 1 张 cid 图 |
| `multi-image.mht` | 5+ 张图，混合 cid / Content-Location |
| `data-uri.mht` | 内嵌 Data URI 图片 |
| `region.mht` | 含区域标记（`<!--START-->`…`<!--END-->`）与区域外图片 |
| `titles.mht` | 多个带 `<title>` 的文件，用于标题提取与命名 |
| `cn-filename.mht` | RFC 2047 编码中文文件名（P0-8 修复点） |
| `garbage.mht` | 非 MHT 垃圾字节 → 走失败/跳过路径 |
| `deep-nesting.mht` | 超 100 层嵌套（P0-7 递归保护点） |
| `no-cte.mht` | HTML part 缺 Content-Transfer-Encoding（已知边界） |
| `large.mht` | > 50MB（大文件预览确认路径）—— 可用稀疏/重复内容生成，勿入库 |
| `over-99-files/*` | 100+ 个 MHT，验证 `f%02d_` 前缀在 99 之后的排序（P0/§四 C 类隐患） |

> 夹具应**入库**（体积小），`large.mht` 与 `over-99-files` 用**测试内生成**避免仓库膨胀。

### 3.4 基线内容（每类产物）

| 产物 | 基线方式 |
|---|---|
| 合并 TXT | 文件字节 SHA-256 |
| 单独 TXT（每 MHT 一个） | 目录树（相对路径 + 各文件 SHA-256） |
| 图片（合并目录） | 目录树 + 各文件 SHA-256 + **魔数检测出的扩展名** |
| 图片（单独目录） | 同上 |
| ZIP / CBZ | 归档内条目名集合 + **各条目解压后字节 SHA-256**（不能只比归档文件本身，时间戳会导致差异） |
| 章号 | 生成的章名序列（zh/en 两 locale 各一套） |
| 命名 | 输出文件名/目录名全集 |
| `ProcessStats` | 成功/失败/跳过/警告计数 + 各 `FileResult` 的 outcome |

### 3.5 关键实现要求

1. **不可变基线文件**：`src/test/resources/baselines/<case>.json`，含相对路径 + SHA-256
2. **环境无关**：基线**不得**包含绝对路径、时间戳、会话目录名。提取后**规范化**再比对
   （如把输出根替换为 `<OUT>`）
3. **CI 友好**：每次重构步骤后 `mvntest` 即跑全套
4. **失败即停**：任何基线不一致 = 重构引入行为变更 = 必须查清（是 bug 还是预期？预期则显式更新基线并记录）

### 3.6 注意（避免"黄金基线"经典陷阱）

- 基线**只证明"没变"，不证明"对"**。所以基线必须建立在**已验收的正确版本**上 ——
  本项目当前状态已通过 C1–C11 + I1–I10 验收，**适合作为基线起点**
- 若某产物本身就有已知缺陷（如 §四 C-5 的"并发保存其实是串行"），基线会**固化缺陷**。
  处置：在基线旁记 `knownIssues` 字段说明，重构期保持，重构后再单独修

## 四、Layer B：无头驱动 API（三层解耦的**验收物**）

### 4.1 它同时是"测试手段"与"解耦成果"

用户目标 ② 是「GUI/控制/业务三层彻底解耦，换 UI 框架也能复用业务」。
**这一目标的可验证形式，就是存在一个不依赖 JavaFX 的 API 能完成全部功能。**

所以 Layer B 不是额外负担，而是**解耦工作的直接产物**：
先把功能收敛到无头 API，再让 GUI 调用它，测试也调用它。

### 4.2 目标形态

```java
// com.mhtextractor.app —— 纯业务/应用层，零 JavaFX import
public final class MhtExtractorApp {          // 或按职责拆 ApplicationService

    // 会话/项目状态
    ProjectSession newSession();
    ImportResult importPaths(ProjectSession s, List<String> paths);
    void applyParams(ProjectSession s, ParamTarget target, AppConfig params);
    void removeItems(ProjectSession s, List<ItemRef> refs);
    void group(ProjectSession s, List<ItemRef> refs, String name);
    void ungroup(ProjectSession s, ItemRef group);
    void undo(ProjectSession s);

    // 预览（返回数据，不碰 UI）
    PreviewResult previewText(ProjectSession s, ItemRef item);
    PreviewResult previewImages(ProjectSession s, ItemRef item, ProgressSink sink);

    // 提取（返回结果，不碰 UI）
    ExtractResult extract(ProjectSession s, ExtractRequest req, ProgressSink sink, CancelToken cancel);

    // 持久化
    void saveState(ProjectSession s);
    ProjectSession restoreState();
}

// 进度/取消用纯接口，UI 侧自己适配到 JavaFX
public interface ProgressSink { void onProgress(int idx, int total, String name, double frac); void onStatus(String key, Object... args); }
public interface CancelToken { boolean isCancelled(); }
```

**硬性约束**：`com.mhtextractor.app`（或等价包）**不得 import javafx.\***。
用测试断言这一点（见 §4.4）。

### 4.3 迁移路径（**不做大爆炸式重写**）

每步都保持 304 单测 + 30 GUI + Layer A 基线全绿：

| 步 | 动作 | 验收 |
|---|---|---|
| B0 | 建 Layer A 基线（不改代码） | 基线捕获成功 |
| B1 | 抽出 `ProjectSession`（把 `items`/`displayItems`/参数缓存等状态从 Controller 移入纯类） | 全绿 + 基线不变 |
| B2 | 抽 `ImportService`（`importByPaths`/`applyImportPlan` 等） | 同上 |
| B3 | 抽 `PreviewService`（`onPreviewEffect` 的非 UI 部分 + 缓存交互） | 同上 |
| B4 | 抽 `ExtractService`（`onStartProcessing`/`startExtractionTask`/`processUnit`） | 同上 |
| B5 | 抽 `ParamBindingService`（三层覆盖 + 指纹 + 失效规则） | 同上 |
| B6 | 抽 `UndoService` / `GroupService` / `ReorderService`（后两者已有纯 util 基础） | 同上 |
| B7 | Controller 变成**瘦适配器**：只做控件事件 → 调 Service → 渲染结果 | 同上 |
| B8 | 加 `LayerBTest`：**只用无头 API** 跑通全部功能清单 | 新增测试全绿 |
| B9 | 加 `ArchitectureTest`：断言无 JavaFX 依赖（见 §4.4） | 通过 |

### 4.4 解耦的**可执行验收**（关键，避免"看起来解耦了"）

```java
// ArchitectureTest —— 用字节码/源码扫描断言分层
@Test void applicationLayerHasNoJavaFxDependency() {
    // 扫描编译产物或源码：com.mhtextractor.app 及其依赖闭包不得出现 javafx.*
    assertNoImports("com/mhtextractor/app", "javafx.");
}
@Test void businessLayerHasNoUiStrings() {
    // 业务层不得有 I18n.get 的 UI 文案键（只允许错误码）
}
@Test void controllerIsThin() {
    // MainController 行数 < N、方法数 < M（重构目标的可量化断言）
}
@Test void swappingUiAdapterIsPossible() {
    // 用一个"假 UI 适配器"实现 ProgressSink/View 接口，跑通一次完整提取
    // —— 证明换 UI 框架只需重写适配器
}
```

`swappingUiAdapterIsPossible` 是**对用户目标 ② 的直接证明**：
用非 JavaFX 的桩 UI 跑通业务，即"已可换 UI 框架"。

## 五、全量测试的执行矩阵（重构每一步都跑这套）

| 层 | 命令 | 期望 | 耗时 |
|---|---|---|---|
| 单测全量 | `source .claude-work/env.sh && mvnx clean test` | 304+ 全绿 | ~14s |
| 产物基线 | 同上（基线测试含在单测内） | 全部 SHA 一致 | 含在内 |
| GUI 自动化 zh | `source .claude-work/env.sh && run-test-mode` | 30/0 | ~30s |
| GUI 自动化 en | `run-test-mode -Duser.language=en -Duser.country=US`（需按 env.sh 补参） | 30/0 | ~30s |
| 分层断言 | 同上（`ArchitectureTest`） | 无 JavaFX 泄漏 | 含在内 |
| 无头功能全跑 | 同上（`LayerBTest`） | 功能清单逐项通过 | 含在内 |

**单项耗时约 1–2 分钟**，适合**每完成一个重构步骤就跑一次**。

### 5.1 建议的"步骤收尾清单"（每个重构步骤必须全过）

```
[ ] git commit 前：mvnx clean test          → 304+ 全绿
[ ] 产物基线比对                            → 0 差异（或显式记录预期变更）
[ ] run-test-mode（zh）                     → 30/0
[ ] run-test-mode（en）                     → 30/0
[ ] ArchitectureTest                        → 无 JavaFX 泄漏（B7 之后）
[ ] 更新 docs/handoff/ + 项目需求文档.md 状态
```

## 七、测试方法的落地顺序（给新会话）

1. **先建 Layer A 基线**（B0）——这是所有后续步骤的标尺，且**必须在重构前**捕获，
   否则基线里会混入重构后的行为
2. 然后按 §4.3 的 B1→B9 逐步解耦，每步跑 §五 的矩阵
3. §4.4 的 `ArchitectureTest` 从 B1 起就加（先宽松后收紧），
   避免"重构完了才发现还有 20 处 JavaFX 依赖漏在外面"
4. 解耦完成后，**`MainController` 的 30 项 GUI 断言应迁出**到独立测试类
   （消除 `项目需求文档.md` §四 A-2 的自锁效应）

## 八、与用户目标 ②（换 UI 框架）的对应关系

以 `D:\JAVA\newui\FluentUIStyle` 作为目标 UI 框架为例，解耦完成后替换 UI 需要做的工作应**仅限于**：

| 工作量 | 内容 |
|---|---|
| 重写视图层 | FXML/CSS → FluentUIStyle 的控件与主题 |
| 重写适配器 | 实现 `ProgressSink` / 视图接口，把 Service 的输出渲染到新控件 |
| 保留不动 | **全部业务逻辑**（core / extractor / processor / output / util / cache / app 层）+ 304 单测 + 产物基线 |

**验收方式**：`swappingUiAdapterIsPossible` 测试（用桩 UI 跑通业务）+ 人工确认
`com.mhtextractor.app` 的依赖闭包无 `javafx.*`。

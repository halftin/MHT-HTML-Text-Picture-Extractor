# E3-2 设计说明与范围界定（业务层文案 → 结构化码值）

> 会话 18 · 阶段 E3 第 2 步的**前置设计**（尚未实施）
> 结论先行：**这一步比原计划复杂得多，且不服务于验收判据 V1/V2。建议在 E5 之后、作为独立需求实施。**

---

## 一、原计划与其失效点

原计划（`docs/重构-耦合点分类表.md` 耦合点 #6）：把业务层 36 处 `I18n.get(...)` 改为
"警告码 + 参数"，文案渲染收口到表现层。

**实测复核后发现三处原计划没有考虑到的连带影响**，使该改动从"局部重构"升级为"跨层 + 破坏兼容"的改动。

## 二、实测范围（会话 18）

### 2.1 字符串的产生点比"调用点"更多

| 位置 | 角色 |
|---|---|
| `core/ContentExtractor.java`（2 处） | 产出警告字符串并放入 `lastWarnings` |
| `core/HtmlUtils.java`（2 处） | 同上（区域标记未找到） |
| `extractor/BaseExtractor.java` | **持有 `protected final List<String> lastWarnings`** |
| `extractor/ImageExtractor.java`（2 处） | 产出警告字符串 |
| `extractor/ImageSource.java` | `default List<String> warnings()` |
| `cache/DirectoryImageSource.java` | 实现 `warnings()` |
| `processor/BatchProcessor.java`（1 处） | `reportExtractorWarnings` 把警告**二次包装**成 `extract.fileWarned` |
| `processor/ImageBatchProcessor.java`（13 处） | 跳过/失败/警告明细 |
| `processor/TextBatchProcessor.java`（9 处） | 同上 |
| `util/HtmlExportBuilder.java`（3 处） | 导出失败原因（`ExportResult.failure`） |
| `util/OutputUnitPlanner.java`（1 处） | **产物命名**（`core.groupDefault`），**不属于 UI 文案，不应改** |

### 2.2 ★ 连带影响一：警告字符串会写入磁盘缓存（schema 变更）

`cache/PreviewCacheMeta.java` 的两个 record 组件都是 `List<String> warnings`，
且 `PreviewCacheMeta` 由 Jackson 序列化为 **`meta.json`**（`PreviewCacheStore` 落盘）。

> **因此把警告改为"码值对象"会改变缓存文件的结构**：
> 旧缓存无法反序列化（或需要兼容层），必须 **bump `PreviewCacheMeta.FORMAT_VERSION`**
> （当前 = 1），并意味着**老用户的预览缓存全部失效重建**。

这已经不是"重构"，而是**用户可见的兼容性变更**（按硬规则 R4 必须显式标注）。

### 2.3 连带影响二：警告经 `FileResult` 进入 GUI 与基线

`BatchProcessor.recordFileResult(...)` 把 `warnings` 装进
`processor/FileResult`（`record FileResult(String path, ExtractOutcome outcome, String message, List<String> warnings)`），
再经 `ProcessStats.fileResults` 回写 GUI（提取 banner / 条目详情）。

- `FileResult` 是 `record`，改字段类型会波及**所有构造点与读取点**；
- 现有测试中与这些字符串/明细相关的断言约 **19 处**需要同步改写。

### 2.4 连带影响三：警告文本还会被 HTML 导出复用

`HtmlExportBuilder` 的 warning 会随导出的 HTML 一起交给浏览器查看链，
属于"产物内容"的一部分，不是纯 UI 文案。

## 三、结论与建议

| 判断 | 依据 |
|---|---|
| **不服务于 V1/V2** | V1 = `app` 层依赖闭包零 JavaFX（已达成，且有运行时证据 + 闭合断言）；V2 = 桩 UI 跑通全功能（已达成）。业务层产出文案既不引入 JavaFX 依赖，也不阻碍无头运行 |
| **属于"架构整洁度"改进** | 它的收益是"文案不再绑定在业务层"，对**跨语言复用**才有实质价值 —— 而用户已明确裁决**跨语言复用不在本次范围** |
| **风险高于原估计** | 触达 10 个类 + `FileResult` record + 约 19 处测试断言 + **磁盘缓存 schema** |
| **建议时机** | 在 **E5（Controller 变瘦）之后**，作为**独立需求**实施；届时一并：
① bump `FORMAT_VERSION` ② 提供旧缓存迁移或明确废弃 ③ 同步更新 19 处断言 ④ 重捕产物基线 |

## 四、若日后实施：推荐的落地形态（供接手）

1. 新增 `com.mhtextractor.i18n.BusinessMessage(String code, Object... args)`（或 `record`），
   只承载"码 + 参数"，**不含渲染逻辑**；
2. 把 `BaseExtractor.lastWarnings`、`ImageSource.warnings()`、`FileResult.warnings`、
   `ProcessStats.*Details`、`PreviewCacheMeta.warnings` 的类型改为 `List<BusinessMessage>`；
3. 表现层新增唯一渲染入口（如 `I18n.render(BusinessMessage)`），GUI/HTML 导出/日志各自调用；
4. `OutputUnitPlanner` 的产物命名（`core.groupDefault`）**保持由业务层产出** —— 它是产物语义，不是 UI 文案；
5. `FORMAT_VERSION` 由 1 → 2，并在 `PreviewCacheStore.load` 中把"版本不符"按未命中处理
   （现有实现已有版本校验，成本较低）；
6. 每步跑完整矩阵；**测试断言需要成批改写**，建议先建立"码 → 期望文案"的对照表再动手。

## 五、防线（当前已具备）

- `I18nUsageContractTest`（会话 18 · E3-1）：把业务层**实际用到的 29 个键**逐条固定，
  断言 zh/en 双语可渲染且占位符齐备 —— 日后实施本需求时，它就是"文案不许变"的安全网；
- `ArchitectureTest.businessLayerI18nUsageDoesNotGrow`：业务层 `I18n.` 引用数**只减不增**；
- 产物黄金基线 32 份：任何影响产物的文案改动都会被逐字节发现。

## 一、为什么 i18n 必须"先定架构"

用户明确要求：**改动时优先考虑架构，为即将进行的架构重构做准备**。这在 i18n 上不是空话，因为：

1. `MainController`（6099 行）含 **162 条**用户可见文案，横跨约 15 个职责。
   把它们**按职责分组**并抽成键命名空间，等价于**先画出上帝类的拆分缝**。
2. 若只做"字符串替换"，得到的是 319 个散落的 `I18n.get("k123")`，
   **对重构毫无帮助**，还多了一层间接。
3. 因此本设计的核心产物是**键命名空间 = 职责地图**，其次才是替换动作。

## 三、技术形态（硬约束）

| 项 | 决定 | 理由 |
|---|---|---|
| 机制 | `java.util.ResourceBundle` | 标准；JavaFX `FXMLLoader` 原生支持 `%key` |
| 资源文件 | `src/main/resources/i18n/messages_zh_CN.properties`、`messages_en_US.properties` | |
| 唯一入口 | `com.mhtextractor.i18n.I18n`（**禁止**业务代码直接 `ResourceBundle.getBundle`） | 单点可控、可集中处理缺键 |
| FXML | `text="%key"`（**不要**把 FXML 文案搬进 Java） | JavaFX 原生机制，`FXMLLoader` 注入同一 bundle |
| 占位符 | **具名** `{name}`，**不用** `MessageFormat` 的数字索引 | 见 §3.1 |
| 语言切换 | 启动时读取（`GuiState.locale`）；运行中热切换为加分项，非必需 | |
| native-image | 需补 `resource-config.json` 的 bundle + `reflect-config` 的 `ResourceBundle` 类 | 见 §6 |

### 3.1 为什么用具名占位符而不是 `MessageFormat`

`MessageFormat` 用数字索引（`{0}`），翻译时极易错位；且它把单引号当转义符，
中文文案里的 `'` 会引发难查的 bug。故自研**具名占位符**：

```
# zh_CN
preview.outputFile={name}.txt
preview.mergedNote=输出目录：{folder}（合并输出，所有文件共用）
alert.cacheSize=预览缓存已占用约 {step} GiB，当前实际 {actual} GiB（临时目录：{dir}）。
```

实现要点：按 `\{(\w+)\}` 扫描，缺失参数**不静默**（记 log.warn 并把占位符原样保留，便于发现）。

### 3.2 缺键策略（必须明确，不可含糊）

**返回 `!key!` 形式的标记 + `log.error`**，而不是返回 `null` 或原样返回键名。

理由：返回 `null` → GUI 显示空白（用户以为功能坏了）；原样返回键名 → 与真实文案混淆。
`!key!` 在界面上一眼可辨，且可被自动化测试断言捕获（见 §5 I9）。

## 四、键命名空间 = 职责地图（**本设计的核心**）

命名规则：`<领域>.<元素>.<用途>`，全小写、点分隔。

**关键点**：领域划分**不按文件**，而按**职责**。`MainController` 的 162 条按下列领域分组后，
每个领域天然对应一个**可独立提取的类**——这就是为架构重构准备的缝。

| 命名空间 | 职责 | MainController 中的大致位置 | 未来可提取为 |
|---|---|---|---|
| `app.*` | 窗口标题、全局消息 | `App.java` | — |
| `mode.*` | 模式标签/切换 | `updateModeUi` | `ModePresenter` |
| `dir.*` | 输入/输出目录选择 | `onBrowseInput/Output`、`autoSetOutputPath` | `DirectorySelector` |
| `import.*` | 导入（含配额确认） | `importByPaths`、`runImportRounds` | `ImportCoordinator` |
| `list.*` | 列表、勾选、计数、位置 | `updateFileCount`、`updateListButtons` | `ListPresenter` |
| `group.*` | 分组/拆组/组名/组信息 | `onGroupClicked`、`onUngroupClicked`、`updateInfoArea` | `GroupPresenter` |
| `reorder.*` | 拖拽排序与合并 | `performDrop`、`beginDrag` 区 | `DragController` |
| `undo.*` | 撤销各分支 | `onUndoClicked` | `UndoPresenter` |
| `params.*` | 参数设置/清除/应用全局 | `onParamSettings`、`clearParamsForTargets` | `ParamBindingModel`（§四 4.2 B-2） |
| `preview.*` | 预览区（文本/图片/缩略图/提示） | `updateContentArea`、`renderThumbnails`、`onPreviewEffect` | `PreviewPresenter` |
| `extract.*` | 提取状态/进度/结果横幅 | `onStartProcessing`、`updateExtractBanner` | `ExtractCoordinator` |
| `cache.*` | 缓存占用提醒、关窗清空 | `onSizeAlertStep`、`onWindowCloseRequest` | `PreviewCacheLifecycle` 的 UI 侧 |
| `alert.*` | 通用告警标题/按钮/确认文案 | 各处 `Alert` | — |
| `core.*` | 产物类文案（章节名、默认输出名） | `ChapterGenerator`、`OutputUnitPlanner` | `ChapterNamingStrategy` |
| `browser.*` | 浏览器查看相关 | `openHtmlInBrowser` | 已有 `BrowserLauncher` |
| `dialog.*` | `ParamDialogController` 全部文案 | — | — |

**FXML 键**：与控件语义同名，例如 `main.title`、`param.tab.text`、`param.image.nameStart`。
FXML 键放进**同一份 bundle**，便于 `FXMLLoader` 单次注入。

> **给架构重构的交付物**：会话 13 完成后，`MainController` 中每个 `I18n.get("preview.…")` 的聚簇
> 就是「预览职责」的代码范围。重构时按命名空间切分，比按方法名猜测可靠得多。

## 五、错误契约（与 i18n 合并做，依据 §3.4 / §四 4.2 B-1）

### 5.1 现状问题

`showAlert` 的文案把**异常消息直接拼进用户文案**：

```java
showAlert(AlertType.ERROR, "参数设置窗口打开失败: " + e.getMessage());   // :1149 附近
```

而异常消息来自各层且是中文（102 处 `EXCEPTION`）。只外置 UI 文案不动异常，
会得到**"英文界面 + 中文错误"**的混合体。

### 5.2 设计

引入**错误码枚举** `ErrorCode`（`com.mhtextractor.i18n` 或 `com.mhtextractor.core`）：

```java
public enum ErrorCode {
    PARAM_DIALOG_OPEN_FAILED,
    OPEN_FOLDER_FAILED,
    BROWSER_VIEW_FAILED,
    INPUT_DIR_INVALID,
    OUTPUT_DIR_INVALID,
    MHT_PARSE_FAILED,
    ARCHIVE_FAILED,
    WRITE_FAILED,
    ...
}
```

- bundle 键：`error.<CODE>`，例如 `error.ARCHIVE_FAILED=归档失败`
- UI 侧统一：`showError(ErrorCode, Throwable)` → 文案取 `I18n.get("error." + code)`，
  **技术细节（`e.getMessage()`）只进日志，不进用户文案**
- **本会话范围**：只覆盖 §2.7 涉及的 **20 条 `UI_ALERT`** + 会被 `showAlert` 展示的异常；
  102 条 `EXCEPTION` **不全改**（那属于 §四 B-1 的完整工程），只登记清单

> **边界明确**：不做"全量异常消息英文化"。目标是**用户可见路径**上不出现中文，
> 内部异常继续用中文记日志（开发者面向，符合 §3.1 的取舍）。

## 七、不做什么（明确边界，防止范围膨胀）

| 不做 | 理由 |
|---|---|
| 249 条 `log.*` 中文 | 面向开发者；且项目已有中文日志习惯 |
| 347 条测试中文 | 测试不面向用户 |
| 102 条 `EXCEPTION` 全量英文化 | 本会话只做用户可见路径（§5.2） |
| 配置文件字段名（JSON key）本地化 | **持久化契约必须与语言无关**，否则切语言导致配置/缓存失效 |
| `meta.json` 字段名本地化 | 同上；且会导致所有预览缓存失效 |
| 运行中热切换语言 | 加分项，非必需（启动时读取即可） |
| `unnamed` 哨兵值翻译 | **它是内部哨兵，翻译会破坏 6 处 equals 比较**（见 §8.2） |

## 八、三个高危点（必须按序处理）

### 8.1 `ChapterGenerator` 必须策略化（产物文案）

`ChapterGenerator.java` 硬编码中文数字与「第…章」（17 处盘点命中）：

```java
private static final String[] DIGITS = {"", "一", "二", ...};
return "第" + toChineseNumber(number) + "章";
```

**要求**：抽 `ChapterNamingStrategy` 接口 + 两个实现：
- `ChineseChapterNamingStrategy`（现有逻辑**原样迁移**）
- `WesternChapterNamingStrategy`（`Chapter 1` / `1.` 等，具体格式由会话 15 定）

**硬约束**：`ChapterGenerator` 现有 public API 与 **0-based index 语义不得变更**
（`TextBatchProcessor` 与既有测试依赖它）。

### 8.2 `unnamed` 是内部哨兵，**先改语义再谈翻译**

实测 6 处使用同一字面量，且**语义被混用**：

| 位置 | 用法 |
|---|---|
| `SanitizeUtils:32` | sanitize 失败时**返回** `"unnamed"` |
| `ImageExtractor:190` | 文件名回退**返回** `"unnamed"` |
| `ImageWriter:95` | 空文件名**返回** `"unnamed"` |
| `OutputUnitPlanner:209` | `s.equals("unnamed")` → 输出名回退 `"组"+no` |
| `OutputUnitPlanner:219` | `s.equals("unnamed")` → 回退 `All_Images`/`mht_output` |
| `ImageBatchProcessor:207` | `folderName.equals("unnamed")` → 置 null |
| `TextBatchProcessor:95` | `!s.equals("unnamed")` → 判断标题有效 |

**两个问题**：① 它是哨兵却被当输出名候选与字符串比较，用户真实标题恰为 `unnamed` 会被静默丢弃；
② **绝不能**为 i18n 翻成 `"未命名"`——那会让 6 处 `equals` **全部失效**，输出命名静默走错分支。

**要求（两步分离，分两次提交）**：
- **步骤 A**：把哨兵改为 `public static final String UNNAMED_SENTINEL = "unnamed"`（或更彻底地改
  `Optional`/`null` 语义），**补测试锁定 6 处比较行为**
- **步骤 B**：再决定面向用户的默认名如何本地化

### 8.3 破坏性变更：默认输出名会变

本地化后 `"组N"`、`"输出文件"`、`All_Images`、`mht_output` 会随语言变化，
**用户既有输出目录名会改变**。

**要求**：**中文 locale 保留既有行为**（`"组N"`、`"输出文件"`），**仅 `en_US` 用英文**。
这样老用户零影响。需在交接中显式标注取舍。

## 三、⚠️ 本会话发现的结构性问题（决定后续路线，重要）

### 3.1 `FeatureExercise` 并不是在驱动 `MainController`，而是在**复刻**它的提取链路

实测（`FeatureExercise` 内引用）：

```java
// :511 / :515 / :1075
List<OutputUnitPlanner.OutputUnit> units = OutputUnitPlanner.plan(
        mc.items, MainController.ITEM_VIEW, false, mc.textParamsCache, mc.imageParamsCache, sessionDir);
```

即当前 `test.mode` 的"自动化回归"里，**提取编排是测试夹具自己重跑一遍**（`OutputUnitPlanner` + 若干 processor/output 类），
而不是走 `MainController` 实际使用的那条路径。

**后果**：它证明的是"测试夹具那份复刻对"，**不能**证明"生产路径对"。这是**验证价值的结构性缺口**，
也是那 61 个被引用成员的真正用途 —— 不是"读私有状态"，而是"借私有状态**另跑一遍**"。

### 3.2 用户已拍板的三项决策（本会话）

| 问题 | 决策 |
|---|---|
| 阶段 A 是否立即做 | ✅ 立即做（已完成） |
| 61 个被引用成员如何彻底解耦 | ✅ **改造 `FeatureExercise`：不再驱动 `MainController`，改驱 app 层** |
| 30 项 GUI 交互断言怎么保 | ✅ **双轨**：保留 UI 演练 + 新增无头验收 |

> **注意二者的张力**（阶段 B 必须正面处理）：若 `FeatureExercise` 完全不再驱动 `MainController`，
> 则"保留 UI 演练"就需要**另一个**驱动 `MainController` 的载体。阶段 B 的可行切法：
> ①先把 `FeatureExercise` 里**复刻的提取链路**改为调用 `MhtExtractorApp`/未来的 `PreviewService`（去掉复刻）；
> ②UI 交互部分（拖拽/分组/撤销/三态复选框/预览上屏）仍驱动 `MainController`，另立载体或保留在 `FeatureExercise` 中。
> 这一步会**显著降低**被引用成员数：对照 §3.1，`ITEM_VIEW`、`textParamsCache`、`imageParamsCache`、`items`
> 中至少前三个的用途就是喂那份复刻；改用 app 层后它们应可收回。

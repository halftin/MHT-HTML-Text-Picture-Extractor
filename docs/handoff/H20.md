## 三、⚠️ 本会话发现的结构性问题与**更正**（决定后续路线，重要）

### 3.0 更正声明（2026-09-26 追加）

本节最初的 3.1 断言"`FeatureExercise` 自己另起了一套提取管线、自动化回归证明的是复刻"——
**该结论不准确，已作废**。错误成因：只看了 `OutputUnitPlanner.plan(...)` 的调用点，**没有读上下文**。

核实后的真相：

| 位置 | 所在路径 | 实际作用 |
|---|---|---|
| `FeatureExercise:511/515` | `exerciseAllFeatures`（演练） | **仅 `log.info` 打印**输出单元计划，不产出任何产物 |
| `FeatureExercise:1075` | `runAutomatedTests`（自动化） | 断言 `units.size() >= 2`，即"输出单元数"这一项 |

**真正的提取**走的是生产按钮路径：`mc.startButton.fire()` → `MainController` 的提取处理 → 生产
`processor`/`output` 类。因此那三处是对生产类 `OutputUnitPlanner` 的**有意独立复核**（用相同输入重算并交叉核对），
**不是复刻**——而且 `MainController` 内部也确实调用 `OutputUnitPlanner.plan(...)`，两者构成"手段不同源"的交叉验证，
**符合本项目的复验纪律**。

> 教训（与 `CLAUDE.md` 验证纪律同源）：**"调用生产类"不等于"复刻生产逻辑"**。
> 仅凭调用点下结构性结论会误判；必须读上下文。

### 3.1 `FeatureExercise` 与 `MainController` 的真实耦合构成（更正后）

那 61 个被引用成员实际分三类，**只有第一类是"测试 UI 就必须碰 UI"**：

| 类别 | 代表成员（引用次数） | 性质 |
|---|---|---|
| **UI 交互** | `undoButton`(31)、`textModeToggle`(16)、`groupButton`(9)、`clearParamsButton`(8)、`startButton`(6)、`selectAllCheck`(4)、`applyGlobalButton`(2) … | 只有驱动真实 UI 才有意义，**不可搬运** |
| **编排/单元复核** | `OutputUnitPlanner.plan` × 3 | 有意的独立复核，**不是复刻** |
| **断言用内部状态** | `items`(13)、`parseToken`(4)、`lastExtractStats`(4)、`undoManager`(4)、`imageLoadActive`(2) … | 属"读状态做断言" |

**因此"把 `FeatureExercise` 改成驱动 app 层"会丢掉第一类（UI 交互）** —— 与用户选定的
"双轨：保留 UI 演练 + 新增无头验收"**直接冲突**。该方案不再推荐。

### 3.2 ✅ 替代路线已实测可行：用 `Node.lookup("#fx:id")` 取代字段引用

**探针**（仓库外，`%TEMP%\lookupprobe\LookupProbe.java`，零仓库改动）加载真实 `MainView.fxml`，
在三个阶段测量 42 个 `fx:id` 的 `lookup()` 可解析性：

| 阶段 | 可解析 |
|---|---|
| stage1（`load()` 后、`show()` 后立刻） | **41 / 42** |
| stage2（`applyCss()` + `layout()` 后） | **41 / 42** |
| stage3（下一脉冲） | **41 / 42** |

**唯一不可解析的是 `modeToggleGroup`** —— 它是 `ToggleGroup`，**不是 `Node`**，故不参与场景图查找。
这项不是问题：`ModeToggleGroup` 只被 FeatureExercise **0 次**引用（见 §1.1 表格），
必要时可经 `textModeToggle.getToggleGroup()` 取得。

**关键结论**：`lookup()` **对 `visible=false` / `managed=false` / `disabled=true` 的节点同样可解析**
（`badgeHeaderLabel`、`outputNameLabel`、`textPreviewArea`、`stopButton`、`progressBar` 等均命中的是**不可见**节点，
且三个阶段的解析结果**完全一致**）。即"节点当前是否显示/可用"**不影响** `lookup()` 的可用性——
这消解了最初的顾虑。

**意义**：`lookup()` 不需要包级可见性 → 那些"仅为 `.fire()` / `.setSelected()` / `.setText()` 而放宽"的
`@FXML` 字段可全部收回 `private` 并摘除标记。按 §1.1 的引用表，可覆盖 `undoButton`、`groupButton`、
`clearParamsButton`、`startButton`、`selectAllCheck`、`applyGlobalButton`、`textModeToggle`、
`imageModeToggle`、`inputFolderField`、`outputFolderField`、`removeButton`、`ungroupButton`、
`groupNameField`、`statusLabel`、`progressBar` 等**约 17 个**仍是标记的 `@FXML` 字段。

> **待办**：这些 `lookup()` 调用需要一个宿主。宿主放 `FeatureExercise` 内部（测试源集，**不占**
> `MainController` 的 4985 行零余量），例如 `Node n(String fxId)` 辅助方法。

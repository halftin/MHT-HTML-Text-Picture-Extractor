## 二、⚠️ 最重要的设计发现：规划文档漏掉了一条更稳的路线

规划 §2.2 只考虑了三条路线，并把"模型持一份、GUI 持一份 + 单向投影（A′）"当作唯一可行解，
同时把**别名/双状态**称为"本任务唯一的结构性难点"。

**实测存在第四条路线，且严格更好**：把数据序列表**作为 `java.util.List` 注入**模型。

```java
// app.WorkspaceModel —— 字段与参数类型都是 java.util.List，字节码仍零 javafx
public WorkspaceModel(List<Object> sharedTopLevel) { this.topLevel = Objects.requireNonNull(sharedTopLevel); }

// gui.MainController
final ObservableList<Object> items = FXCollections.observableArrayList();
final WorkspaceModel ws = new WorkspaceModel(items);      // ← 同一份存储
```

为什么它能通过架构红线：`ArchitectureTest.businessPackagesHaveNoUiFrameworkDependency` 扫的是
**字节码常量池**，`java/util/List` 不是 UI 类型。规划 §2.2 否决"路线 A"的理由是"模型持有
`ObservableList`"——那是**字段类型**层面的问题，注入为 `List` 就绕开了。

**它消灭了什么**：迁移期间任何尚未迁移的 GUI 直写，模型立刻可见 → **每一步都自洽**，
可以逐操作迁移、逐次提交，不需要"影子镜像"这类过渡补丁，也不存在投影时滞。
本任务因此没有出现规划担心的状态分叉。

## 三、⚠️ 修正的 3 处模型语义 + 1 个真实缺陷（接入前必须核对的价值所在）

### 3.1 模型 `group()` 与生产不一致的 3 处

| # | 项 | 旧模型 | 生产（`MainController.onGroupClicked`） |
|---|---|---|---|
| 1 | 单项建组 | 要求 ≥2 项，否则返回 null | **允许**（R9：勾选集合为空时退化为当前选中项） |
| 2 | 插入槽位 | 取"目标（或其所属组）在顶层的最靠前**索引**"；组内成员用**组的索引** | 取最靠前的**落点**：目标在顶层→自身索引；目标在组内→**组索引 + 1**；且每摘除一个位于槽位之前的条目**槽位左移** |
| 3 | 摘除成员后致空的组 | **不销毁**（留下空组） | **自动销毁**，且销毁位置参与槽位左移 |

第 2 项的实际差异（实测，`WorkspaceModelParityTest`）：

```
顶层 [g1(a,b), g2(c,d), e]，把 a、c 合成新组
  旧模型：[g3, g1, g2, e]      （槽位 = g1 的索引 0）
  生产  ：[g1, g3, g2, e]      （槽位 = g1 索引+1 = 1）
```

**这就是"接入前必须逐行核对语义"的全部价值**：若直接委托，用户会看到组位置变化。

### 3.2 真实缺陷：`parentGroup` 是幽灵归属，不能作为归属判据

`parentGroup` 会在两种情况下残留：
1. `clear()` 只清模型内部状态，**不触碰条目对象**（H32 §三.2 已记录）；
2. **撤销建组后**成员的 `parentGroup` 仍指向已脱离顶层的旧组 —— 这是**有意保留**的既有语义
   （`WorkspaceModelParityTest.fullSequenceRoundTripRestoresExactIdentityOrder` 明确断言并注明
   "调用方不得据此判断成员仍在组内，归属必须看结构"）。

本次用 `parentGroup` 优先判归属（第一版 `slotOf`）后，**实测两处故障**：

| 故障 | 被什么抓到 |
|---|---|
| `clear()` 后拿旧条目建组 → **在空工作区上建出了组**（应为 no-op） | `WorkspaceModelParityTest.clearResetsStructureUndoStackAndGroupNumbering` |
| 撤销建组后再建组 → 成员**未被摘除**，拆组后顶层出现**重复项**（2 → 4） | `StubUiAcceptanceTest.groupThenUngroupThenUndoRestoresOriginalLayout` |

修法即 `WorkspaceModel.slotOf()`：**先判"是否直接在顶层"，再判"所属组是否仍在顶层"**。
这与旧实现 `firstTopLevelIndex` 做对的事一致（它也是结构判据），是重写时的回归。
→ 再次印证 H32 §三.3："任何靠 `parentGroup` 判断成员归属的代码都不可靠，必须看结构。"

### 6.1 阶段 2.5：撤销的应用仍有两份实现

`onUndoClicked`（233 行）自己实现了 REMOVE / REMOVE_GROUP / GROUP / UNGROUP / IMPORT 的结构恢复，
而 `WorkspaceModel.undo()` 里也有同样一份（**生产从不调用它，是测试专用**）。

GUI 对数据序的直写**只剩这 3 处**（其余已全部经模型）：

```
MainController:2957   items.add(Math.min(record.destroyedIndexes().get(k), items.size()), g);
MainController:2976   items.removeAll(record.items());

```

**建议做法**：给模型加 `boolean applyUndo(Record)`（应用一条**已弹出**的记录，不碰栈），
把 `undo()` 与它共用同一批私有 `undoXxx`；GUI 改为
`record = ws.popRecord(); boolean structural = ws.applyUndo(record);` 然后只做 UI 收尾
（选中跳转 / 规则 (c) / 重新预解析 / 日志）。

⚠️ **注意一个坑**：GUI 的 `case GROUP, REORDER, MERGE_GROUPS` 是**合并分支**，三者共用
`GroupStructure.restoreStructure(items, record.structureBefore())`；而模型对 GROUP 的实现还额外做了

否则 GROUP 会被恢复两次。REORDER / MERGE_GROUPS 模型**未支持**，仍需 GUI 自己应用。

## 八、本会话固化的做法

1. **"共享存储"优先于"单向投影"**：只要能以 `java.util.List` 注入，就不必造投影与影子状态，
   迁移期的双状态风险直接归零（见 §二）。
2. **接入生产前必须逐行核对两侧语义**，不能假设"模型是对的"。本次模型有 3 处与生产不符，
   其中 1 处会改变用户可见顺序。
3. **变异测试确实有效**：本会话两次用它证明断言有强度 ——
   把 `List.of(group)` 改成 `List.of()` → `removeGroupRecordCarries…` 失败；
   把 `slotOf` 的 `gi+1` 改成 `gi` → **2 条**槽位断言同时失败。
4. **`parentGroup` 永远不是归属判据**（第三次被同一类问题咬到，见 §3.2）。
5. 会话开始 / 结束都跑完整门槛，且**用不同手段复算**（mvn 输出 vs 独立聚合 surefire）。

## 三、⚠️ 三条实测语义（**改写了规划文档里的假设，接投影前必读**）

1. **`WorkspaceModel.topLevel()` 已是 `List.copyOf` 快照**，**不是**规划 §阶段 1 警告的"实时视图"。
   → `items.setAll(ws.topLevel())` 天然安全。但**推论相反**：模型给快照、GUI 拿可变列表，
   凡"先持有 `items` 引用、之后再改"的代码语义都会变，需按持有者逐个审计
   （已定位存量持有者：`PreviewListCell:414` 的 `DropResolver.resolve(ctl.items, ...)`，只读，安全）。
2. **`clear()` 只清模型内部状态**：不触碰条目的 `parentGroup`/`removed`；
   且 **`group()` 只对"已在本模型数据序中"的条目生效**（内部靠 `firstTopLevelIndex` 定位），
   否则**静默返回 `null`**。→ 阶段 2.1 不能只调 `ws.clear()`，条目级复位必须由控制器负责。
3. **撤销建组后成员的 `parentGroup` 仍残留指向已脱离顶层的旧组对象**（与撤销移除一致）。
   → 任何"靠 `parentGroup` 判断成员归属"的代码都不可靠，必须看结构。

## 四、⚠️ 阶段 1a 的实际设计（与规划的差异）

规划说"把 `MainController` 的撤销栈整个搬到模型"。实测 `onUndoClicked` 是 **233 行**，内含
**参数恢复 + 缓存失效（规则 a）+ 重预解析 + 中文 log 文案** —— 这些**不能进无头模型**
（模型零 `I18n`、零缓存依赖）。因此实际采用"**栈唯一 + 应用分工**"：

- `WorkspaceModel` **独占唯一栈**：新增 `push(record)` / `popRecord()` / `canUndo()` / `clearUndoStack()`
- **结构类**（REMOVE/REMOVE_GROUP/GROUP/UNGROUP/IMPORT）由模型 `undo()` 应用（能力已有）
- **参数/拖拽类**（PARAM_SET/CLEAR_PARAMS/APPLY_GLOBAL/REORDER/MERGE_GROUPS）由控制器
  `popRecord()` 取出后自行应用
- **`popRecord()` 是必需的**：模型 `undo()` 对未支持类型会"原样压回"以保栈序；若栈唯一而 GUI
  又要处理那些类型，未支持类型会**永久卡在栈顶**，把后面的结构撤销全部堵死

> **尚未完成的部分（诚实标注）**：`onUndoClicked` 里**结构类记录的状态应用**仍是控制器自己写的
> （`:2979-2987` REMOVE 的 removed 复位与销毁组插回、`:3005` REMOVE 的 `items.removeAll`、
> `:3021` 结构快照恢复、`:3043` `restoreGroup`），**没有**改为委托 `ws.undo()`。
> 也就是说：**栈的位置统一了，应用的实现还有两份**。这正是阶段 1b/2 要消除的重复。

## 五、🚨 环境与验证陷阱（本会话连续踩中三个，务必先读）

1. **Maven 增量编译会被 write/edit 工具的时间戳骗过**
   日志打印 `Nothing to compile` / `BUILD SUCCESS`，但 `target/.../X.class` **根本没更新** —— 我因此
   误判两轮。**判据只能用 `Get-Item target/.../X.class | % LastWriteTime` 是否变新**；
   必要时 `(Get-Item <源文件>).LastWriteTime = Get-Date` 强制重编。

2. **变异测试的"存活"可能是假的（两次自造错误）**
   - `mvn test` 会**先跑 `compile` 阶段**。若"先还原源码、再跑测试"，maven 会检测到源码比 class 新，
     **用原版源码重编并静默覆盖变异体** → 5/5 全部"存活"，全是假象。
   - **备份不能自引用**：把变异体覆盖进 `.class.orig` 备份后再"还原"，等于把变异体装回去，
     会让探针结果与源码矛盾（本会话真实发生过，误导了一轮排查）。
   - **正确做法**（已固化为 `.claude-work/mutation-workspace-parity.ps1` v4）：
     变异体源码**留在盘上**跑测试（maven 无事可做），每轮开始用 `git restore` 回到干净源，
     结束后 `git restore` + 全量重编。脚本内自校验 `mutantInPlace=True`。

3. **`headless-layer-b` 是 pom 里的硬编码白名单**（`pom.xml:199`，5 个类），
   新增的无头测试类**不会**自动纳入 → 计数不涨是**设计使然**，不是漏跑。
   新类若要纳入，需改 `pom.xml`（仍属生产改动，建议与阶段 1b 合并提交）。

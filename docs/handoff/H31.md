## 二、⚠️ 核心结论：`app` 层落地不完整（本会话最重要的发现）

### 2.1 事实（双重确认：jdeps 入度 0 + 文本搜索）

主源码中 `MhtExtractorApp` 与 `WorkspaceModel` **只出现在自己的声明与一句 javadoc 里**；
测试中分别用了 5 次 / 20+ 次。**GUI 实际直接 new processor**：

```java
// MainController.java:2120-2149  processUnit(...)
ImageBatchProcessor processor = new ImageBatchProcessor(config, previewCacheLifecycle);
processor.setCancelSupplier(...); processor.setRecursionContinueCallback(...);
processor.process(files, ...);                    // ← 绕过 MhtExtractorApp
TextBatchProcessor processor = new TextBatchProcessor(config);
...
```

### 2.2 `app` 层 5 个类的真实身份

| 类 | GUI 是否真用 | 性质 |
|---|---|---|
| `WorkspaceParamService` | ✅ **15 处调用** | 真集成（四条缓存规则收口） |
| `ExtractionPreconditions` | ✅ **9 处调用** | 真集成（提取前置校验） |
| `PreviewService` | ✅ 真集成（步骤 2 接线） | 真集成 |
| **`MhtExtractorApp`** | ❌ **0 处** | **测试专用**（"业务可脱离 UI"的可执行证明物） |
| **`WorkspaceModel`** | ❌ **0 处** | **测试专用** |

**准确表述**：GUI 与门面**共享**同一批 processor/output/cache 类（不是各写一份），
但**编排逻辑有两份**：GUI 版多了输出单元规划 / 每单元参数 / `PerFileOverrides` / 递归回填；
门面版**有意**只做"扁平列表 + 单一配置"（其 javadoc 明确写了）。两者在"无分组 + 全局参数"下
产物**逐字节一致**（基线锁定）。→ **子集关系，不是浪费性重复。**

### 2.3 对"目标②已完成"的更正

- ✅ **预览链路的编排**确实已搬进 app 层（`PreviewService`，步骤 2）
- ❌ **提取链路的编排仍在 `MainController.processUnit` 里**
→ 换 UI 框架时，**提取的分派与编排要重写**（processor 本身可复用）。

## 四、⚠️ native 元数据的**反直觉**事实（勿按旧文档操作）

旧文档说"`reflect-config.json` 是过时子集，建议确认后删除"。**实测这是危险的**：

| 文件 | 类型数 |
|---|---|
| `reflect-config.json`（旧格式） | **291** |
| `reachability-metadata.json`（统一格式） | **194** |
| **仅存在于旧格式、统一格式里没有** | **231** |

native-image 对同 type 取**并集** → 目前那 231 条**仍生效**；**直接删旧文件会丢 231 条**。

同时已查清：**实际用反射的自有类型极少** —— 主源码只有 `App.java:119-123` 一处
（`Class.forName("...FeatureExercise")` + `MainController`）。其余 231 条涉及的
`MimeParser`/`ImageExtractor`/`BatchProcessor` 等**都是 `new` 出来的**，很可能是不再需要的条目。

**结论：不能删、也不建议现在清理。** 正解是用项目现成的**并集合并 + 方法/字段级对账（丢失数=0）**；
但**本机 native 被 MSVC 阻塞、无法验证** → 在无法验证时改 native 元数据，风险 > 收益。

### 4.1 一个具体的 native 隐患（已定位）

`FeatureExercise` **未在任何一个元数据文件里注册**，而它是唯一真正经 `Class.forName` 加载的自有类型。
- JVM 侧 ✅ 正常（测试类在 `target/test-classes`）
- native 侧 ⚠️ **`test.mode` 会失败**；**正常用户路径不受影响**

## 九、本会话验证纪律的战果（勿重复踩坑）

**6 处自身错误全部由独立复验抓到**，据此固化的流程：

1. **跨文件搬代码用自定位脚本**（声明锚定正则 + 花括号配平），**不要**硬编码行号表，**不要**用行数估算边界
2. **恢复基线用 git**，不要用临时备份（失败中间态会让行号表与真实文件不匹配）
3. **新写的断言提交前做一次变异测试**（问："把被测行为改坏，这条断言还会通过吗？"）
4. **对"不一致"再核一遍再下结论**（本会话两次靠这条避免了误判）
5. **"找声明"要用声明锚定正则**，`indexOf(名字 + "(")` 会先匹到调用点
6. **字节级核对文件编码**再下"乱码"结论（本会话的乱码是 PS 5.1 按 GBK 渲染所致）

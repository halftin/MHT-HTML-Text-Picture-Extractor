## 一、一句话结论

生产代码里**再没有一处模态 Alert**（27 处调用点全部换成窗口内提醒），而这件事**零新增依赖**：
`atlantafx-base 2.1.0`（pom 里本来就有的依赖）自带 `Notification` / `NotificationSkin` / `ModalPane` / `ModalPaneSkin` / `Styles` / `Animations`，
你现在用的 `NordLight` 主题里也已经有 `.notification` 与 `.modal-pane` 的完整样式。

三层语义（用户拍板）：

| 语义 | 实现 | 行为 |
|---|---|---|
| 错误 | 居中 `ModalPane` + `Notification(DANGER)` | **必须点"确定"**才消失（`persistent=true`，遮挡层/ESC 不关） |
| 警告 / 信息 | 右上角 toast（`VBox` 图层） | 非阻塞、可堆叠（上限 5 条）、✕ 关闭 |
| 确认 | 居中 `ModalPane` + `Notification` + 确定/取消 | **回调式**，取代 `showAndWait()`；`persistent=true` |
| 等待中 | 居中 `ModalPane` + `Message`（**无按钮、无 ✕**） | 后台干活，**干完自动收卡片 + 执行收尾**（关窗前清缓存；实现与 4 个坑见 §5.6 与 §六） |

## 三、架构与接线

```
gui/component/NotificationHost.java   ← 新类（唯一入口，静态方法）
        install(Scene, StackPane)     // 每个窗口装一次
        of(anchor)                    // 场景上没装 → 就地补装（根不是 StackPane 就包一层，且打日志，不静默吞）
        toastInfo/toastWarning(anchor, msg)
        error(anchor, msg, FontAwesomeSolid icon)            // 居中 + 必须点确定
        busy(anchor, title, desc, FontAwesomeSolid icon, work, onDone)  // 居中 Message 卡片：零可交互控件
        confirm(anchor, msg, FontAwesomeSolid icon, onDecision)         // 居中 + 回调
```
> **图标按"用途"传**（2026-09-27 追加）：不再是一套通用图标，而是每个调用点给一个贴合语境的图标
> （文件/文件夹/浏览器/导入/导出/缓存/配额/递归/垃圾桶/配置/内存…）。完整映射表在 `CLAUDE.md` 的「交互提醒约定」。
> 不带图标的旧签名保留（默认中性图标，供降级路径用）。加图标只改实参，**不增行数**（`MainController` 红线不受影响）。

- 调用点**只传一个锚点节点**（本项目用现成的 `statusLabel` / `configComboBox`），**控制器不需要持有宿主字段** ——
  这是为了 `MainController` 的"只减不增"红线：整轮下来 **4355 → 4360 行**（上限 4370，余量 10）；
  本会话末尾追加"按用途给图标"后为 **4361 行**（只多 1 行 `FontAwesomeSolid` import），**余量 9 行**。
- 图层顺序即 z 序：`内容 < toast 图层 < 居中 ModalPane`；toast 图层 `pickOnBounds=false`，空白处鼠标穿透。
- 非 FX 线程调用安全：`withHost` 先 `Platform.runLater` 再解析锚点（**节点只在 FX 线程上读**）。
- 接线点：`App.start()`（主窗口）与 `ParamDialogController.create()`（参数窗口）各包一层 `StackPane` 并 `install`。

## 五、踩过的坑（全部实测，不是推测）

### 5.1 🚨 `new StackPane(loader.load())` 编译通过、运行时 `ClassCastException`

`FXMLLoader.load()` 是泛型 `<T> T load()`，而 `StackPane` 有 `StackPane(Node... children)` 变参构造 ——
编译器把 `T` 推成 **`Node[]`**，于是把 `BorderPane` 强转成 `Node[]`：

```
java.lang.ClassCastException: class javafx.scene.layout.BorderPane cannot be cast to class [Ljavafx.scene.Node;
	at com.mhtextractor.App.start(App.java:59)
```

**修法**：先落到 `Parent root = loader.load();` 再 `new StackPane(root)`（`App.java` 已就地留注释警告）。

### 5.2 🚨 GUI 自动化的 `logs/test-results.txt` 会**假绿**（本轮真被它骗了一次）

上面那个崩溃发生时，我把 `logs/test-results.txt` 读出来看到 **"30 passed, 0 failed"** —— 那是**上一次会话留下的陈旧文件**，
本次运行根本没跑到断言。**纪律：每次跑 GUI 自动化前先 `Remove-Item logs/test-results.txt`，并核对结果文件的 mtime。**

### 5.3 `ModalPane` 会把内容**拉满整窗高度**

`Notification` 直接 `show()` 进 `ModalPane` 后实测 **400 × 761**（整窗高），卡片被拉成一条竖带。
**修法**：`ntf.setMaxHeight(Region.USE_PREF_SIZE)` → **400 × 149**（`NotificationHost.showModal` 已内置，探针有断言）。

### 5.4 `Button.setDefaultButton(true)`（demo 原样照抄）会**劫持全窗口回车**

`defaultButton` 是**场景级**的。实测：把一个普通按钮置于焦点、焦点不在通知上，按回车 →
**通知的按钮被触发**，而获得焦点的应用按钮**没有反应**。
本项目主源码原本 **零** `setDefaultButton`，所以照抄 demo 等于新增全局行为变更。
**决定：通知里的按钮一律不设 `defaultButton`**（`NotificationHost.button()` 有注释钉死）。

### 5.5 `Notification` 的 ✕ **不会**自己把节点摘掉

`NotificationSkin.handleClose` 只 `getOnClose()` 触发事件（字节码证实），不 `getChildren().remove`。
demo 里那句 `Animations.flash` 只是动效。**宿主必须自己移除**（本项目：toast 从图层移除、居中卡 `modalPane.hide()`）。

### 5.6 🚨 `ModalPane` 的**皮肤必须先于 `setContent` 存在**，否则卡片静默不显示
两个都在字节码里、且都只在"**皮肤还没建好时**"才发作（启动早期就发提醒必现；启动久了皮肤早在位，所以 `error/confirm` 一直正常）：

1. 卡片内容是**皮肤的内容监听器**挂到皮肤自己容器上的。若先 `setContent` 再让 CSS 布局建皮肤，
   监听器注册时变更事件已经过去 → 内容**永远挂不上**（现象：`display=true`、卡片高度 **0**、屏幕上看不到任何东西）。
2. `ModalPaneSkin` 构造时还会自己 `hide()` 一次（`doHide()` → `setDisplay(false)`），会**把刚 `show()` 的卡片打回未显示**。

**正确顺序**（`NotificationHost.showModal` 已按此写死，并有注释）：

```java
modalPane.applyCss();       // ① 皮肤先就位（监听器已注册）
modalPane.setContent(node); // ② 再挂内容，监听器才会把它放进皮肤容器
if (!modalPane.isDisplay()) {
    modalPane.show(node);   // ③ 最后才 show（且要在皮肤那次 hide() 之后）
}
```

**怎么测出来的**：不是读文档，而是"现象 → 二分"：把 `showModal` 的逐行序列搬进最小环境并打印
`display/opacity/viewOrder/height`，发现隔离环境里**每次都正常**，才定位到"皮肤在 `show()` 之后才建好"这条路径。

### 5.7 🚨 交付审计发现的**真风险**：未回答的确认卡被关窗卡片顶掉 → **窗口关了但进程残留**

这是把模态 Alert 换成窗口内卡片带来的**语义回归**，也是本轮最值得记的一条。三段实测证据：

1. **旧语义**：Alert 是 `APPLICATION_MODAL`，等回答期间主窗**根本关不掉**。
2. **新语义（修复前）**：卡片挡住了场景内的点击，但**窗口的 ✕ 是 OS 级的，照样能点** →
   `PendingConfirmCloseProbe` 实测：`card before close = Notification "PENDING-CONFIRM"` →
   关窗后 `card right after = Message`（被清缓存卡片顶掉）、`decision = (none)`（**回调从未触发**）、
   `blocked thread = extract-worker-like alive&nonDaemon=true`、`window showing = false`。
3. **非 daemon 线程的后果**：`NonDaemonExitProbe` 实测 —— 非 daemon 线程活着时关掉最后一个窗口，
   **60s 后 JVM 仍未退出**（只能杀进程）。而主程序里**提取线程正是 `new Thread(task).start()`（非 daemon）**，
   只有导入线程是 daemon。⇒ 用户看到的是"窗口消失、进程还在"。

**三层防护（现在都在代码里，且都有断言）**：

| 层 | 位置 | 作用 |
|---|---|---|
| L1 | `MainController.onWindowCloseRequest` 的 `NotificationHost.hasPendingDecision(statusLabel)` 守卫 | 有未回答的确认卡 → `e.consume()` 不放行（恢复旧模态语义） |
| L2 | `NotificationHost.showModal` 开头的"顶替未答确认 → 按取消交付" | 任何其他卡片（错误/等待）顶掉未答确认时，**回调照样交付 `false`**，调用方不会永久阻塞 |
| L3 | `busy` / `confirm` 的降级路径 | 卡片显示不出来（锚点没挂场景）时：`busy` 仍然执行 `work + onDone`（否则关窗流程硬锁），`confirm` 直接交付 `false`（否则后台线程永久等待） |

⚠️ **实现顺序有坑**：`confirm` 必须 **先 `showModal` 再登记 `pendingDecision`** —— 反过来的话，
新卡片一上来就被 `showModal` 开头的"顶替即取消"逻辑取消掉（实测：L1 守卫失效、卡片被替换）。
这一条已在源码里写注释钉死。

## 七、未做 / 未验证（别当成已验证）

0. **`Message` 里做可点链接（用户提到的 demo 写法）**：`Message(String, String, Node)` 的说明槽是 **`String`**，
   `MessageSkin` 里**没有 Hyperlink**（`javap` 实测），所以
   `msg.addEventFilter(ActionEvent.ACTION, e -> { if (e.getTarget() instanceof Hyperlink link) … })` 这套在 `Message` 上**没有落点**。
   `Message` 官方的交互入口是 **`setActionHandler(Runnable)`**（皮肤里就是调它），本项目当前**没有用**——
   等待卡片按需求做成"零可交互控件"。**若以后想让缓存目录/日志可点**：`msg.setActionHandler(() -> …)` 一行即可，
   代价是卡片不再是"零控件"（`TileBase` 的 interactive 样式会生效）。
1. **ESC 与遮挡层点击的"必须点按钮"**：`persistent=true` 是我们设的（代码事实），皮肤里也确实有 `getPersistent()` 分支与
   `createCloseBlockedAnimation()`（字节码事实）。但**动态验证没打通**：验收探针里"非 persistent 的对照组"用
   真实 `Robot` ESC（焦点已放进卡片内）**也没关掉** → 说明本环境 ESC 送不到皮肤的处理器（它注册在皮肤内部的
   `ScrollPane` 上，不是 ModalPane 上）。所以探针把这两条标成 **UNVERIFIED**，没有伪装成 PASS。
   **建议**：人工按一次 ESC / 点一次卡片外区域确认（与 H35 §六"点击本身没有断言"同一处理方式）。
   > 顺带结论：**遮挡层点击拦截是实测过的**（`.claude-work/uiprobe/placement-*.log`：`modalpane` 布局下背景按钮的真实鼠标点击**没有触发**，
   > 而 `control`（无覆盖层）与 `center`（纯居中无遮罩）**都触发了**）—— 该实验用的是**等价构造**（同一个 `ModalPane` + `persistent=true`），不是 `NotificationHost` 本身。
2. **参数设置窗口内的通知**（3 处错误 + 2 处警告 + 2 处确认）没有单独的自动化断言：GUI 自动化的 30 项走的是直驱 API，
   不经过那些按钮回调。
3. **native EXE**：本机仍缺 MSVC，无法构建/验证（与 H30/H31/H34 同一阻塞点）。元数据未改动是**有意**的。
4. `FeatureExercise` 里 `new Alert(...)` 的 4 行（:335-339）**保留**：那是给 tracing agent 采集用的构造，不属于生产路径。
   （生产已无 Alert，这批元数据条目属于"可回收但按纪律不动"。）

- 同时出现两条居中提醒时，后来的会**替换**前一条（同一个 `ModalPane`），前一条的回调不会被触发 ——
  等同于"用户没有确认"，不会重复执行。若将来需要并列/排队，可用 `ModalPane.Z_FRONT/Z_BACK` 多实例。

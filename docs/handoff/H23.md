## 一、为什么要做这一步（目标 ② 的真实缺口）

搬迁前 **`MhtExtractorApp` 没有任何 preview 方法** —— "预览"的编排全部长在 `MainController` 里：

```
算缓存键 → 查缓存 → 未命中则 解析 MHT + 抽图 + 原子落盘 → 组装缩略图数据 → 写盘后指纹自校验
```

这意味着换 UI 框架时，这条链路要么重新实现、要么反过来驱动旧控制器（后者等于没解耦）。
本步把它搬进 app 层，使"给定文件 + 参数 → 得到预览缓存与缩略图元数据"成为**不依赖任何 UI 框架**的能力。

## 二、⚠️ 本步的边界：像素解码**搬不走**（必须说清，以免高估目标 ②）

`decodeThumb` 的像素解码**依赖 JavaFX**：

```java
img = new Image(new ByteArrayInputStream(data), 150, 150, true, true);   // JavaFX 缩放解码
img.getPixelReader().getPixels(...);                                     // JavaFX 取像素
```

WebP 走 `WebPFXImage`（JavaFX 绑定），其余走 JavaFX 原生解码。**所以"缩略图像素解码"无法进入 app 层**
（会立刻触发 `ArchitectureConstraint`：业务包不得依赖 javafx）。

**因此本步采取的边界是**：

| 归 app 层（`PreviewService`） | 归 GUI 层 |
|---|---|
| 缓存键计算、命中判定 | JavaFX 图像解码（缩放算法） |
| 解析 MHT、按参数抽图 | 像素打包 → `ThumbnailData` |
| meta 构建、原子落盘（`store.write`） | 上屏、弹窗、进度条 |
| 磁盘占用台阶检查 | 线程与 `Platform.runLater` |
| **缩略图元数据**（`coreName`：扩展名识别 + `ImageWriter.computeFileName`） | 结果失效后的缓存删除（属调用方规则） |

`ThumbnailData.pixels()` 由服务产出时**为 null**，渲染层解码后填充 ——
即"需要哪些缩略图、它们叫什么"不再依赖 UI 框架，"长什么样"仍由各 UI 自己决定（任何 UI 都必须做这件事）。

> 未来若要用纯 Java 解码器（`ImageIO` / glavo webp）彻底无头化缩略图，**属行为变更**
> （缩放算法从 JavaFX 平滑缩放换成其它实现，缩略图会变），需人工目视确认 + 重做基线。**本步有意不做。**

## 三、实现要点

### 3.1 新 API

```java
public record PreviewResult(PreviewCacheMeta meta, Path imagesDir, List<ThumbnailData> thumbs) {}

public PreviewResult ensureCached(Path mht, AppConfig params, Supplier<Boolean> cancelled) throws Exception
```

**语义与搬迁前逐行等价**（1 命中即返回 / 2 meta 损坏则删目录重建 / 3 未命中则解析+抽图+原子落盘 /
4 落盘后触发一次台阶检查）。两条**有意**的设计：

- **不做失效判定与删除**：四条生命周期规则属 `PreviewCacheLifecycle`，由调用方按自己的工作流触发。
  服务只负责"按 key 取到或建立缓存"。
- **不认识"代次"**：搬迁前控制器在"抽图完成、写盘之前"检查 `token != requestToken` 并**放弃写缓存**。
  该语义改由 `Supplier<Boolean> cancelled` 承接 —— 服务只认"调用方说别写了"，不认 UI 概念。

### 3.2 一个我在实现中自己引入、又自己抓到的**行为回归**

第一版我把代次检查放在**锁外**（`ensureCached` 返回之后）：

```java
pr = previewService.ensureCached(...);
if (token != requestToken) return;   // ← 太晚了：此时缓存已经被写进去了
```

而搬迁前是"抽图完成、**写盘之前**"检查。后果：代次失效时**仍会写缓存**（旧行为是不写），
语义变了、且违背 `H9` 记录的"写盘期间竞态"防护。

**修法**：把取消信号作为 `Supplier<Boolean>` **传进服务**，在 `rebuild` 的抽图之后、`store.write` 之前判定
（`PreviewServiceTest.cancellationAfterExtractionSkipsCacheWrite` 锁定：取消后缓存根无可用条目）。

> 教训：**搬移"顺序敏感"的守卫时，不能只看它是否被调用，还要看它相对其他副作用的位置。**
> 我把一个守卫从"副作用之前"挪到了"副作用之后"，编译与大部分测试都不会报。

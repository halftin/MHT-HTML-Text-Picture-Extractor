## 二、⚠️ 审计脚本自身的错误（记录，避免重犯）

第一版审计脚本（`.claude-work/s1b-audit.js` 的初版）用**"取行内最后一个标识符"**来判定字段名，
于是把 `final PreviewCacheLifecycle previewCacheLifecycle = new PreviewCacheLifecycle(...)` 解析成了
**类型名 `PreviewCacheLifecycle`**，而不是字段名 `previewCacheLifecycle`。

**后果：产生一批假阳性** —— 把实际被引用的成员报成"从未被引用"，其中 `previewCacheLifecycle`
实为 **8 次**引用、`saveGuiState` 实为 1 次。若按该错误输出执行，会**误删有效标记并可能破坏编译**。

**纠正办法**：改用**行首锚定的「类型 + 名字 + 终止符」**正则（`Type name =` / `Type name ;` / `RetType name(` /
`class Name`），改后 **UNPARSED = 0**，且与"哑正则"结果一致。

> 这与 `CLAUDE.md` 里记录的"正则 `[,)]` 漏掉分号结尾的枚举常量"是**同一类错误**：
> 解析器写得越"聪明"，越容易在一个没想到的形态上静默失效。**判定标准要尽量哑、尽量贴近真实形态。**

**并且**：本阶段开始时我一度以为"阶段 A 误把 `viewSourceButton` 收成了 private"（因为审计初版把
`viewSourceButton` 报为 `direct=0`）。用"哑"方法复核后确认：**阶段 A 的 22 个字段全部确实零引用**，
`viewSourceButton` 从未被 `FeatureExercise` 访问过 —— 是**审计脚本错**，不是阶段 A 错。
**对"不一致"再核一遍再下结论**（本项目的验证纪律）在此再次生效。

## 四、下一个待决点：`lookup()` 迁移做不做

### 4.1 已具备的前提（阶段 A/B 期间实测）

- 探针实测（见 H20 §3.2）：`Node.lookup("#fx:id")` 对 **41/42** 个 `fx:id` 可解析，
  **唯一例外 `modeToggleGroup` 是 `ToggleGroup` 而非 `Node`**；且**对 `visible=false` / `managed=false` /
  `disabled=true` 的节点同样可解析**，三阶段结果一致。
- 追加核实：`modeToggleGroup` 被 `FeatureExercise` 引用 **0 次**（它只由 FXML `$modeToggleGroup` 绑定使用），
  **不构成迁移障碍**。
- 全部 `@FXML` 字段在 `FeatureExercise` 中**一律以 `mc.<名>.` 形态**出现（逐个核对，`bare-other = 0`）。

### 4.2 迁移的收益与代价

| 项 | 内容 |
|---|---|
| **收益** | 约 **14 个**仍是标记的 `@FXML` 字段可收回 `private` 并摘标记 → 预期 **62 → 约 48**；且"测试按 `fx:id` 定位节点"比"测试引用 Java 字段"更接近可替换 UI 的形态（目标②） |
| **代价** | 需在 `FeatureExercise`（**测试源集**，不占 `MainController` 的 4985 行零余量）加一个 `lookup` 宿主；改动点较多（`undoButton` 31 次 + `textModeToggle` 16 次 + `progressBar` 15 次 + … 合计约 120 处调用点） |
| **风险** | 中。宿主是机械替换，但 120 处调用点需逐个替换并靠 GUI 30 项断言兜底；`progressBar` 存在**跨行**的 `mc.progressBar` 用法（计数 15 > 单行 13），替换脚本需处理 |

> **注意**：`mainControllerIsShrinking`（4985 顶格）与 `testSupportSurfaceDoesNotGrow`（62 顶格）
> **仍是两条同时零余量**的不变式。`lookup` 宿主放测试源集正是为了不触碰前者。

## 一、做了什么

| 动作 | 细节 |
|---|---|
| 新建包 | `src/main/java/com/mhtextractor/platform/` |
| 移动 | `gui/util/BrowserLauncher.java` → `platform/BrowserLauncher.java`（仅改 `package` 声明） |
| 更新调用点 | `MainController`：`import com.mhtextractor.platform.BrowserLauncher;` |
| **删除**无用 import | `FeatureExercise` 曾 `import ...gui.util.BrowserLauncher;` 但**从不使用** —— 直接删除而非改路径 |
| 纳入不变式 | `ArchitectureTest.BUSINESS_PACKAGES` 新增 `com/mhtextractor/platform`，使该包受"零 JavaFX"扫描 |

**为什么新建包而不是塞进 `util`**：`util` 是**业务纯逻辑包**（`DropResolver`/`GroupStructure`/`OutputUnitPlanner` 等，
都有单测、且被架构不变式按业务包约束）。而 `BrowserLauncher` 是与**操作系统**打交道的基础设施
（注册表探测、进程启动、原生 CDP 客户端），语义上不属于业务逻辑。新建 `platform` 后两类职责不再混淆。

**注意**：`JavaFxUtil` **留在** `gui.util` —— 它确实依赖 JavaFX，归属正确，不该跟着搬。

## 二、⚠️ 迁移暴露出一处既有问题（不是本次引入的）

迁移后 `ArchitectureTest.businessLayerI18nUsageDoesNotGrow` **失败**：`I18n.` 引用从 36 涨到 37。

**根因（已实测确认）**：`BrowserLauncher` 里有一处**既有的**
`I18n.get("browser.sourceHtmlHead")`（`platform/BrowserLauncher.java:602`，源码页的页头文案）。
它一直存在，只是此前该类在 `gui.util`（不在 scanned 集合内）而**从未被计入**。
把 `platform` 加入扫描集合后，它首次被统计。**差值恰为这 1 处**，迁移前后逐项核对一致。

**这暴露了一个真实的架构问题**：基础设施层**不应该产出面向用户的本地化文案**。
`platform` 包的职责是"与操作系统交互"，让它依赖 `i18n` 去生成页面文案，方向是反的 ——
换 UI 框架 / 换语言时，这层会被迫跟着动。

**处置（本次有意保守）**：
1. 把基线从 36 调到 **37**，并在测试里**写明"这是口径扩大暴露的既有引用，不是新增耦合"**；
2. 在测试注释与本文档**登记为待清理项**；
3. **不顺手改** —— 彻底修法是让调用方（GUI）把页头文案作为参数传入，那会改动
   `openViewSource`/`writeSourceViewPage` 的签名并波及 `MainController`（而 `MainController` 行数顶格），
   属独立一步。本次与"包迁移"解耦，避免一次改动同时改变行为（R3/R4）。

## 四、§四：为什么本步没有做 4 类拆分

启动包的要求是"迁出 + **按 4 类职责拆分**"（源码页生成 / 注册表探测 / CDP 客户端 / 进程启动）。
我**先只做了迁移**，理由是**可独立验证**：

1. 迁移本身零逻辑改动，用"全量单测 + 基线 + GUI"即可**强证明**无行为变化；
2. 4 类拆分是**跨 866 行的机械重构**，且 `writeSourceViewPage`/`launch`/`openViewSource` 等
   与 CDP 逻辑交织，拆分需要重新设计类间契约 —— 与步骤 3（`PreviewListCell` 外迁）同量级。
   步骤 3 的经验表明这类重构会产生**多轮编译错误**，应单独成步、单独验证、单独提交；
3. 把"改包名"和"改结构"混在一次提交里，一旦出问题**无法区分是哪一部分导致的**。

**下一步建议**：把 4 类拆分做成独立的步骤 5b（已具备前提：包归属已正确、不变式已覆盖该包）。

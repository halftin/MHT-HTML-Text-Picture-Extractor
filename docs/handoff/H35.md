> 生成：2026-09-27　|　依据：**实测**（全历史 pickaxe + **逐版本函数体扫描** + 字节码常量池反汇编 + GUI 双语言自动化 + 独立聚合 surefire），不是自述

## 一、一句话结论

用户报告"点击预览区缩略图 → 系统默认图片查看器打开缓存图片"的功能**多轮修改后失效**。

实测结论是：**它不存在，而且从未进入过任何一次提交** —— 不是被条件挡住，而是被
**E1.4 重写 `buildThumbBox` 时整段抹掉**，且抹得很"干净"：**编译通过、411→412 单测全绿、
32 份产物基线未变、GUI 自动化 30/0**，所以三轮重构都没有暴露。

恢复方式：把"索引 → 缓存图片真实路径"的定位收进 `PreviewCacheStore.imageFileFor(meta, index)`，
在 `buildThumbBox` 上挂单击处理器，经 **非 AWT** 的 `cmd /c start "" "<图>"` 交给系统文件关联。

## 三、为什么会被**静默**抹掉（三个条件同时成立）

1. **该功能只活在工作区，从未提交。** 本仓库长期处于"大量未提交修改"的状态（本轮 i18n 改动亦然），
   这类功能在下一次脚本重构里被覆盖后，**git 里不会留下任何痕迹**（正是 §2.2/§2.3 检索不到的原因）。
2. **E1.4（`ac2b90e`）重写了 `buildThumbBox` 的签名，而新签名"已经没能力"实现它**：

   ```
   - private record ThumbEntry(Image image, String coreName) {}          // 老
   + private record ThumbnailData(String coreName, int width, int height, int[] pixels)  // 新
   - private VBox buildThumbBox(PreviewItem item, ThumbEntry entry)      // 老
   + private VBox buildThumbBox(PreviewItem item, ThumbnailData entry)   // 新
   ```

   老结构里"图片对象"本身还沾着来源信息；新结构只剩 **显示名 + 像素**，
   **缓存文件名在 `PreviewCacheMeta.ImageEntry.file()`、目录在 `PreviewCacheStore.dirFor(key)`** ——
   也就是"打开哪张图"这件事在新签名里**没有入口**。重写时顺手删掉 handler，**不需要动任何其它代码**。
3. **零断言覆盖。** `FeatureExercise` 的 30 项里，图片预览只有一条
   `Image preview workspace (C1/C2)`，它断言的是 `cachedThumbs` 非空 + 缓存目录三要素，
   **不点缩略图**。于是"功能消失"在回归里表现为**全绿**。

> 重建代码时的改动路径是 `.claude-work/` 下的脚本（`readFileSync → replace → writeFileSync` 整文件写回，
> 如 `s3-final.js` / `s3-finish-mc.js` / `e2_2-use-service.js`）。这类写法对"未提交的本地功能"**没有保护**。

**给下一个人的结论**：本项目里"编译通过 + 测试全绿"**证明不了功能还在**；
凡是**只在工作区、且没有断言**的功能，都有被下一次脚本重构静默带走的风险。

### 四.1 关键设计：**下标语义**

`PreviewCacheMeta.images()` 与 `item.cachedThumbs` **同序 1:1**（构建时按 meta 顺序逐张追加）。
唯一可能错位的来源是 `onPreviewEffect` 里"读盘失败 `continue`"——而 `PreviewCacheStore.load` 的命中判定
**已要求 meta 里每张图片文件都存在**，故该分支实际不可达。这条不变式写进了
`openCachedImage` 的 javadoc 与 `renderThumbnails` 的循环注释，**改缩略图渲染前必读**。

> 为什么不用 `coreName` 匹配来替代下标：`coreName` 是**输出名**（受重命名/合并输出影响，不保证唯一），
> 用它反查 meta 还得在 GUI 里复制一遍 `ImageWriter.computeFileName`，属反向依赖。

### 四.2 关键设计：key **由 meta 反推**，不依赖"当前参数"

```java
PreviewCacheKey key = new PreviewCacheKey(meta.source().absolutePath(), meta.source().size(),
        meta.source().mtime(), meta.paramFingerprint(), meta.formatVersion());
return dirFor(key).resolve(meta.images().get(index).file());
```

`store.load` 命中时已校验 `meta.matches(key)`，所以反推出来的目录**必然**就是这批缩略图的来源，
与"参数是否已经变了""文件 mtime 是否变了"无关，也不用再读一次文件系统（与 `listKeys()` 同法）。

### 四.3 顺带修掉一处分层泄漏

最初我把 `store().dirFor(key).resolve(entry.file())` 直接写在 GUI 里 —— 那是 GUI 在**拼缓存目录布局**。
现改为调用 `imageFileFor(meta, index)`，**布局知识留在 `cache` 层**，GUI 只按下标要文件。

### 四.4 为什么不用 AWT

主源集在步骤 7 之后要求**零 `java.awt`**（native 元数据也没注册任何 awt 条目）。
`Desktop.getDesktop().open(file)` 虽然语义最直白，但会破坏这条约束；故用
`new ProcessBuilder("cmd", "/c", "start \"\" \"" + file + "\"")` —— 与既有"打开所在文件夹"
（`cmd /c start "" explorer /select,"…"`）**同一机制**，交给 Windows 文件关联 → 系统默认图片查看器。

缓存图片路径形如 `<tmp>/mht-extractor-preview/<64hex>/images/0001.png`，**不含 `&` 等 cmd 元字符**，无需额外转义。

## 九、追补（同日续）："日志说打开了、窗口却没出现"——环境根因与兜底实现

§五/§六 当时把"点击后看图器是否真的弹窗"列为**未验证**。用户实测后报告：
**日志打了 `Opened with the default image viewer: ...0001.webp`，但屏幕上什么都没出现**。
本节是那次诊断与修复的完整记录。

### 9.1 三层证据，把责任从"代码"移到"环境"

| # | 证据 | 结论 |
|---|---|---|
| ① | **用户在资源管理器里双击任意图片也打不开** | 与本程序无关 |
| ② | 探针逐项对比（见 9.2 表） | 坏的既不是我们的代码，也不是 WebP 格式，而是**"用文件去激活 UWP 处理器"**这条链路 |
| ③ | `HKLM\SOFTWARE\Microsoft\Windows\CurrentVersion\Policies\System\EnableLUA = 0`（UAC 关闭）→ 全会话高完整性（实测 `explorer.exe`/`idea64.exe`/本工具 pwsh 的令牌都是 `High Mandatory Level`） | 根因：**UAC 关闭时 Windows 不支持从提权调用方对 UWP/AppX 应用做「文件激活」** |

**照片应用本身是健康的**（不是它坏了）：包状态全部 `Ok`；`.webp`/`.png` 的处理器注册结构完整
（`ContractId=Windows.File`、`PackageId=Microsoft.Windows.Photos_2024.11060.20006.0_x64__8wekyb3d8bbwe`、
`shell\open\command\DelegateExecute={BFEC0C93-0B7D-4F2C-B09C-AFFFC4BDAE78}`）；协议激活正常。

### 9.2 关键对照实验（全部在同一个提权会话内，判据 = **是否出现新的顶层窗口**）

| 命令 | 退出码 / 输出 | 新窗口 | 判读 |
|---|---|---|---|
| `cmd /c start "" "<webp>"`（当时的实现） | 0 / 空 | ❌ 无（Photos 进程起来了但 `MainWindowHandle=0`） | **静默失败**：不报错也不开窗 |
| `cmd /c start "" "<png>"` | 0 / 空 | ❌ 无 | 与格式无关 |
| 上述两者**分参数**传（修正引号） | 0 / 空 | ❌ 无 | **引号不是问题**；现行传参形式对（用 `.txt` 验证：记事本窗口正常出现） |
| `rundll32 url.dll,FileProtocolHandler "<webp>"` | 0 / 空 | ❌ 无 | 同为进程内 ShellExecute，同样被阻断 |
| `explorer.exe "<webp>"` | 1 / 空 | ❌（反而开了「文档」文件夹） | **explorer 把文件当目录浏览**，不是"用默认程序打开" |
| `mspaint.exe "<png>"` | — | ✅「en-1100.png - 画图」 | 经典/完全信任应用不受影响 |
| `start ms-settings:` / `start ms-photos:`（协议激活） | 0 | ✅「设置」/「照片」 | **UWP 本身好的**，坏的是"文件激活" |
| **`ms-photos:viewer?fileName=<urlencoded>`** | 0 | ✅「sample.webp」 | **可用的兜底** |

> 这一步同时否掉了两个曾经合理的假设：① "UWP 完全不可用"（协议激活正常）；② "退出码能识别失败"（被阻断时退出码也是 0）。

### 9.3 修复：`platform.FileOpener`（提交前状态）

```
open(file):
  if (UAC 关闭 && 该扩展名 UserChoice 的 ProgId 形如 AppX*)   ← 环境预判：文件激活必被吞
        → 直接试「照片」协议
  else → 试系统默认查看器（cmd /c start "" "<file>"，校验退出码与输出）
  失败再试「照片」协议；两级都失败 → FAILED（调用方如实打 log.maincontroller.65）
```

- **为什么必须"环境预判"**：被阻断时 `exit=0`、无输出，**退出码校验抓不到**（9.2 实测）。
- **为什么预判要加"处理器是打包应用"这一条**：UAC 关闭但默认看图器是经典 Win32（如 IrfanView）时文件激活照常可用，不该绕开第 1 级。
- **为什么兜底不设为默认**：把处理器写死成「照片」会忽略用户的默认查看器选择（别的机器上可能是 IrfanView/ImageGlass）。
- **校验为什么必须读管道**：Java 默认给子进程 PIPE，不读就丢——这正是"日志说已打开、其实没开"的由来；同时"未在 3 秒内退出"（卡在对话框）也判失败。
- GUI 侧（`MainController.openCachedImage`）把整个打开动作**放到后台线程**（最多 3 秒），避免冻结 FX 线程；日志按实际走通的路径分别打 `log.maincontroller.64`（默认查看器）/`.66`（协议兜底）/`.65`（失败）。

### 9.5 治本方案（本程序侧不改也能恢复）

把 UAC 打开并重启，资源管理器双击与本程序的"文件激活"都会恢复正常（届时 `FileOpener` 会走第 1 级，语义回到"用户的默认查看器"）：

```powershell
Set-ItemProperty 'HKLM\SOFTWARE\Microsoft\Windows\CurrentVersion\Policies\System' -Name EnableLUA -Value 1
# 重启后生效。若当初是为某些老软件/工具才关的 UAC，请自行权衡。
```

## ⚠️ 行为变更（R5）
1. **深度超限（>100 层）子树一律截断**：旧实现回调为 null 时深度限制完全关闭、用户选"继续"后也不再检查；新实现无论回调是否存在都截断，回调返回 true 也无法提取超限子树（防 StackOverflowError 的必然代价）。正常文件深度 <10，无影响；`parse()` javadoc 已同步更新（原"传入 null 则不检查递归深度"已不成立）
2. **RFC 2047 编码的中文文件名现在被解码**：旧实现原样保留 `=?UTF-8?B?...?=` 污染下游扩展名识别；新实现输出正确中文名（输出文件名会变，方向正确）
3. **进度回调单调不减**：可能重复上报上次值（Math.max 语义），不再倒退——依赖"每次上报必递增"的下游无影响，依赖"值必变化"的下游需注意
4. **countTotalParts 只统计深度 ≤100 的 part**：畸形文件的进度估算与实际遍历一致（截断处不再高估 totalParts）；正常文件无影响

## 新发现（未修，留待后续）
1. `MimeParser.java` extractHtmlFromPart（现约 :257-264）：HTML part 缺 Content-Transfer-Encoding 头时，`encoding == null` 兜底写死 `"utf-8"`，`MimeUtility.decode(is, "utf-8")` 抛 `MessagingException: Unknown encoding: utf-8`（RFC 2045 缺省应为 7bit）。真实浏览器 .mht 都带 CTE 头，危害低——归属：C 类清理或后续解析层会话（本会话测试通过给测试 HTML 加 CTE 头规避，未修生产代码）
2. **Jakarta Mail 2.0.2 的 `Part.getFileName()` 不解码 RFC 2047 编码词**（实测确认，与任务描述"会正确解码"不符），已在 getFilenameFromPart 内补 `MimeUtility.decodeText`——后续会话若在别处用 getFileName() 需注意
3. 本仓库无 user.name/user.email 配置，提交须 `git -c user.name="Administrator" -c user.email="admin@mht-extractor.local" commit`（不要 `git config` 修改配置）；会话 2/3/4 已如此提交

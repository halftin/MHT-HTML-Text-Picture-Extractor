## 一、这一步补的是什么缺口

**缺口**：`StubUiAcceptanceTest` 的 `fullUserJourneyWithoutUiFramework` 覆盖了
导入 → 校验 → 建组 → 参数 → 移除/撤销 → 图片提取 → 文本提取，但**没有预览**。
而步骤 2 刚把预览的业务逻辑搬进 `app.PreviewService` —— 若没有测试把它接进完整流程，
"预览可脱离 UI 复用"就只是**设计意图**而非**可执行事实**。

**补法**：在旅程里插入预览环节，并用**生产路径**验证它：

```java
PreviewCacheLifecycle lifecycle = new PreviewCacheLifecycle(new PreviewCacheStore(cacheRoot));
PreviewService previewSvc = new PreviewService(lifecycle);

PreviewResult pv = previewSvc.ensureCached(Path.of(cnItem.path), previewCfg, null);  // ⑥ 预览
...
app.extractImages(..., lifecycle);                                                   // ⑦ 提取并复用
```

关键在于**同一个 `lifecycle` 实例**：预览落盘的缓存被提取环节复用，
于是"预览 → 提取"这条跨环节链路在无头侧完整走通。

### 1.1 新增的断言

| 断言 | 意义 |
|---|---|
| `meta().images().size() == 2` 且 `thumbs().size()` 一致 | 夹具 `cn-filename.mht` 的 2 张图被抽出 |
| 每张缓存图片真实存在且非空 | 落盘确实发生 |
| **缓存图片魔数可识别**（PNG/JPEG/GIF/BMP/WebP） | **非 JavaFX 消费者能自己认格式** —— 这正是"换 UI 框架仍可用"的前提 |
| `thumbs()` 的 `pixels()` 全为 null | 服务只产元数据，像素由渲染层解码（步骤 2 的边界） |
| 再查一次命中 | 缓存读取路径可用 |
| 输出产物与 `image-cn-filename.zh` 基线逐字节一致 | 无头提取语义未变 |
| 输出图片字节 == 缓存图片字节 | 重算与复用的**等价性** |
| **提取后该项目缓存目录被删除** | 规则 (b) 生效，且**证明提取确实走了缓存命中路径** |

## 二、⚠️ 变异测试救了我一次：一条"看起来很强"的断言其实是空的

写完测试后我按本项目纪律做了**变异测试**（故意破坏被测行为，确认测试会失败）：

> 把 `extractImages(..., lifecycle)` 改成 `null`（**禁用缓存复用**），期待新断言失败。

**结果出乎意料**：

| 断言 | 禁用复用后 | 结论 |
|---|---|---|
| 输出图片字节 == 缓存图片字节 | **仍然通过** | ❌ **不能证明复用** —— 重新提取产生的字节本来就与缓存里的一致 |
| 提取后缓存目录被删除（规则 b） | **失败** | ✅ 这才是"确实复用了缓存"的**哨兵断言** |

也就是说：如果我只写了那条"字节一致"的断言，会得到一个**看起来在验证缓存复用、实际什么都没验证**的测试 ——
正是 `CLAUDE.md` 里"验证脚本自身也可能是错的"那一类陷阱。

**处置**：① 在测试里**显式写明**该断言证明的是"重算与复用等价"、**不是**复用证据；
② 把规则 (b) 断言标注为哨兵，并在失败信息里写明"若此断言失败，说明提取没有走缓存命中路径"。

> **方法论收获（值得推广）**：新写的断言在提交前应做一次变异 ——
> **"这条断言会不会在我把被测行为改坏之后仍然通过？"**

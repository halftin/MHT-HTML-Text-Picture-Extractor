## 实现要点

### 缓存查找插入点与命中判定
- 插入点：`processUnified` 的**单元内文件循环**（`ImageBatchProcessor.java:279`，`CacheHit hit = lookupPreviewCache(fileInfo)`），逐文件查（P3 按文件，非按输出单元；无任何单元级命中逻辑）。
- 查找方法：`lookupPreviewCache`（`:602-633`）。
- 命中条件（全部满足才命中，否则走原路径，行为与无缓存时完全一致）：
  1. `previewCache != null`（构造注入；旧构造器传 null → 复用整体关闭）；
  2. `PreviewCacheKey.compute(file, 指纹, FORMAT_VERSION)` 成功（绝对路径 + size + mtime + 指纹，P9 四要素）；
  3. `store.load(key)` 命中（目录 + `.complete` + meta.matches(key) + 全部图片文件存在，会话 8 已实现）；
  4. 元数据含 **≥1 张图**；
  5. 元数据中 **≥1 张有非空 sourceId（cid）**。
- 条件 4/5 的动机：未命中路径有「无图片内容」快速跳过（`cidMap/locationDataMap` 均空 → SKIPPED）。跳过 parse 后无法再查这两个 map，而 meta 里 cid 图（sourceId 非空）⇔ cidMap 非空。只有能**证明**未命中路径会走到提取阶段的缓存才可复用；0 图或全 data URI（sourceId 为 null）的缓存按未命中处理，回全量路径，结果与无缓存时逐字节一致。location-only 图（contentId 为 null）也在「全 null」集合里 → 按未命中处理（罕见，代价只是复用失效，语义无损）。
- **指纹取值（步骤 10.2 要求说明的选择）：直接用单元 params（本处理器 `config.imageExtractionFingerprint()`），不按文件再解析。** 理由：`OutputUnitPlanner` 按「来源 + 参数内容」分桶（`BucketKey(source, params)`），同一单元内所有文件的生效图片参数**完全相同**（H7 收敛），按文件再解析只会得到同一指纹；且条目级参数表（`imageItemParams` 等）在 MainController 层，处理器不可见。预览落盘（会话 9 `effectiveForObject` → `ParamScope.effectiveImageParams`）与提取（`OutputUnitPlanner.resolve` → 同一入口）同源，指纹必然一致。
- IO 失败 / meta 损坏 → log.warn + 按未命中处理（不删除损坏目录，交给既有生命周期扫描/退出清理，避免扩大范围）。

### 命中路径（跳过 parse 与图片提取）
- 数据源换 `new DirectoryImageSource(meta, store.dirFor(key))`（会话 8），handler 与 ImageWriter 只依赖 `ImageSource`（会话 6），零改动即完成复用。
- **标题的提取期重算（P13 的隐藏约束）**：单独模式 + 名称提取开启时，输出目录名依赖 HTML 标题，而缓存元数据不含标题（P13 且预览写盘路径为会话 9 冻结代码）→ 命中时**仍解析一次取标题**（`needsTitleParse`，`:284-296`），图片不重新提取。解析不出 HTML（防御，文件未变时不会发生）→ 回退原路径（与未命中「无法解析」SKIPPED 一致）。合并模式标题不参与命名（MergedOutputHandler 忽略 extractedTitle），完全跳过 parse；名称提取关闭时也完全跳过 parse。
- 警告：取自 `meta.warnings()`（预览落盘时存的就是 `imageExtractor.getLastWarnings()`，同参数同文件 → 确定性一致），经既有 `reportExtractorWarnings` 计入 stats；`recordFileResult` 的 SUCCESS→SUCCESS_WARNED 升级规则不变。
- 输出命名（全局序号 `globalIndex`、单元内 `f%02d_` 前缀、批量重命名序号）全部在提取期由 handler/ImageWriter 重算（P13），缓存元数据只提供「图片字节 + 来源标识 + 原始文件名 + 检测扩展名 + 警告」。
- 保存/成功/失败记录与未命中共用同一段代码（`saved > 0` → SUCCESS，`saved == 0` → FAILED，阶段 A 冻结语义不变）。

### 规则 (b)「完成」的语义（步骤 10.4 要求拍板）
- **定义：该文件本轮结果为 SUCCESS / SUCCESS_WARNED（即 `saved > 0` 且已记录结果）→ 调 `previewCache.onExtractionCompleted(fileInfo.getPath())` 删除该项目缓存目录（按路径反查，含历史指纹残留目录）。**
- **命中与否都删**：需求 (b) 原文是「点开始提取并完成对该项目的提取 → 删该项目对应目录」，未命中（如参数已变、规则 (a) 未覆盖的残留）也应在完成后删除，作规则 (a) 的兜底。
- **取消 → 保留**：循环顶部 `isCancelled()` 中断，未处理到的文件不触发规则 (b)（与 C10「失败可重试」一致）。已处理完的文件在取消前就已完成，删除正常。
- **FAILED / SKIPPED → 保留**：写入失败、归档失败（单独模式）、无法解析、无图片等一律不删，缓存可重试（C10）。
- 性能守卫：`previewCache.hasCachedEntries()`（根目录空则跳过逐文件 listKeys 扫描）；缓存为空（用户从未预览）时规则 (b) 零开销。
- **已知取舍（合并模式归档失败）**：合并归档发生在 `afterAll`（循环之后），此时各文件缓存已按规则 (b) 删除；归档失败时图片本体已保留在合并目录（P0-2 语义），重跑只是走全量提取（更慢但正确，无数据丢失）。P12 复制语义保证输出不被破坏。

### 搬运策略（步骤 10.5）
- **复制，非 move**：复用路径是 `DirectoryImageSource.get(i)` 逐张 `Files.readAllBytes`（缓存只读）+ `ImageWriter` 复制写出到输出目录。缓存目录在写盘期间**从不被修改**，只在 SUCCESS 后删除。写盘失败/归档失败/取消时缓存完好（P12、C10）。测试 `paramChangeMissesCacheAndFailureKeepsCache`、`cancelKeepsCache` 锁定。

4. 缓存「0 图」或「全 data URI」的预览产物在提取时不复用（按未命中走全量路径）——语义与无缓存时完全一致，只是没有加速。

## 新发现（未修，留待后续）
1. **预览与提取并发写盘竞态**：提取期间用户对同一文件点预览（缓存未命中 → 后台写盘），提取结束时规则 (b) 的 listKeys 扫描可能看不到尚在 `.tmp` 的写入 → 缓存残留；或改名后删到刚写完的目录。两种情况残留/删除的都是**与当前参数指纹一致的有效缓存**（非 stale），语义安全，最坏是下次提取复用或重建。归属：会话 11 并发边界。
2. **data-URI-only 文件的「无图片内容」快速跳过**是既有语义（`cidMap/locationDataMap` 均空 → SKIPPED，即使 HTML 里有可提取的 data URI 图）。本会话用「全 null sourceId → 按未命中」绕开了这个坑，但该跳过检查本身是否合理（提取前跳过 data URI 图）属阶段 A 冻结语义，归属会话 11 边界验证。
3. **§2.6(3) 流式产出仍未落地**（会话 9 遗留）：缓存命中路径内存峰值 = 单张图（DirectoryImageSource 逐张读），未命中路径仍瞬时持有全量 `List<ImageData>`。
4. `reportExtractorWarnings(name, () -> fileWarnings, stats)` 的双分支赋值 + lambda 捕获写法经 NIK 25 javac 实测可编译（本会话验证过最小复现，exit=0），属 JDK 25 既有行为，非隐患。

## 六之六、E1.4 完成：缩略图去 JavaFX Image（风险 R2 已化解）

### 设计决策（这是本步最关键的部分）

原 `ThumbEntry(Image image, String coreName)` 直接持有 JavaFX 图像对象。三种候选方案的取舍：

| 方案 | 问题 | 结论 |
|---|---|---|
| 存**原图字节** | 内存随图片尺寸线性增长 → **直接违反 C2**（原实现正是靠"只留 150px 缩略图、丢弃原图字节"满足 C2 的） | ❌ |
| 存 **PNG 字节** | 需图像编码器。`ImageIO` 属 `java.desktop`/AWT，与本项目"为 native 镜像尽量避开 AWT"的取向冲突（同 E1.1 拒绝 `PropertyChangeSupport` 的理由） | ❌ |
| 存**缩放后的 ARGB 像素** `int[]` | 无需任何编码器；每张上限约 150×150×4 ≈ 88 KB，整个工作集 < 1 MB，与原 `Image` 对象量级相同 → **C2 内存口径不变** | ✅ **采用** |

由此新增：
- `MainController.ThumbnailData(coreName, width, height, pixels)` —— **纯数据 record，零 JavaFX**
- `MainController.toFxImage(...)` —— 渲染层**唯一**的"模型 → JavaFX Image"转换点
- `MainController.toThumbnailData(...)` —— 后台解码线程的 JavaFX Image → 纯像素转换
- **`util/ThumbnailPixels`（新文件）** —— 像素打包/解包抽成纯 Java 类，**可零 JavaFX 单测**

### 为什么要把打包逻辑抽出去（本步的方法学要点）

`getPixels`/`setPixels` 的 **stride 与尺寸写错会导致图像斜切、行错位**。
而 GUI 自动化的 C2 断言只检查"`cachedThumbs` 非空 + `cachedImages` 为空"——
**它捕捉不到像素级错位**。所以把该逻辑抽到 `ThumbnailPixels`（零 JavaFX）后补了 **7 条单测**
（含非方形 2×7、1×1、round-trip、越界防御），把这部分从"只有肉眼能发现"变成"CI 可锁定"。

### 关于 `cachedImages`

`PreviewItem.cachedImages`（`List<ImageExtractor.ImageData>`）经全项目核对**只被写 null、从不被读取**，
唯一"使用"是 C2 断言 `cachedImages == null`。它属于历史遗留的死字段，但：
- `ImageExtractor.ImageData` 本身**零 JavaFX**（实测 0 处 javafx 引用），**不构成分层障碍**；
- 删除它会同时改动 4 处写点 + 1 处 GUI 断言 = 行为变更，
- 故按 **R3 不扩大范围**保留，登记为清理项。

### 关键结论：E1.3b 的前置已就绪

实测确认：`PreviewItem` 的**全部字段**现已零 JavaFX ——
`cachedThumbs` 是纯数据 record，`cachedImages` 的元素类型也零 JavaFX（见上）。
**即"搬类"此前唯一的技术障碍（E1.4）已解除。**
但 E1.3b 仍**建议与 E2 一并进行**：现在单搬它只是"换个位置"，而 E2 要抽 `ProjectSession`
时本来就要重新安排这些模型类，一次做完可避免二次 churn。

`selected` 的 3 处 observable 用法（全部等价替换）：

### ⚠️ 本次真实踩坑（必须记住的教训）

改写过程中我引入了**一次真实行为回归**，由 GUI 自动化安全网当场抓住：

- **症状**：`run-test-mode` 挂起 >10 分钟，`logs/test-results.txt` 出现
  `[FAIL] Clear params group: 顶层项目不足: 0`、`[FAIL] Double-click toggle: Index 0 out of bounds` 等**连锁失败**。
- **根因**：我的通用 setter 改写把 `x.selected.set(v)` 变成了**普通字段赋值** `x.selected = v`，
  于是**绕过了 `setSelected()`**，监听器永不触发 → `onSelectionChanged()` 不再执行 →
  全选状态/按钮可用性/顶层项目数全部失真。
- **修正**：另写一遍 pass，把 48 处 `x.selected = <value>` 改成 `x.setSelected(<value>)`
  （值表达式需按"语句终止符"提取，兼容 `;` / lambda 尾 `)` / 同行多语句三种形态）。
- **为什么安全网能抓到**：GUI 30 项断言里包含"全选三态""双击切换勾选""勾选集合含参数目标时按钮应启用"等，
  都是**依赖 `selected` 通知链路**的行为断言。这正是 E0 建安全网的价值兑现。

另有两个**改写脚本自身的 bug** 也在 dry-run 阶段被挡下（未进入代码）：
1. 无接收者的 `/\bbadge\.set\(/` 误伤局部变量 —— `MainController` 内
   `String badge = it.badge.get();` 之后紧跟 `if (badge == null)`，会被改成 `if (badge = null)`。

## 六之三、E0 期间发现的三个实质问题（均已处置）

### 1. ★ 新缺陷：纯 Data URI 的 MHT 永远提取不到图片

- **位置**：`ImageBatchProcessor.java:324` —— `if (parsed.getCidMap().isEmpty() && parsed.getLocationDataMap().isEmpty())` → 直接 SKIPPED
- **隔离证据**（对照夹具，非推断）：

  | `data-uri-mixed.mht` | 1 张 cid 图 + 2 张 Data URI | **3 个产物**：`img001.jpg`、`image_1.png`、`image_2.gif` |

  两者对照证明：问题在**前置快速检查**，**不在** `ImageExtractor.extractDataUriImages`（该代码本身可用）。
- **与既有文档冲突**：`docs/全量功能清单.md` §F 把"Data URI 提取"标为可用功能。
- **处置**：按 R3 **登记不修**（登记表 #17）。修它会改变产物基线，与"重构零行为变更"的验收口径冲突。
  基线 `image-data-uri.{zh,en}.json` 带 `knownIssues` 明确标注"**这是缺陷，不是期望值**"。

### 2. ★ 方法学缺陷：此前"en 30/0"很可能是**假绿**

- **机制**：`App.start:36-42` 在 `FXMLLoader.load()` **之前**用 `logs/gui-state.json` 的 `"locale"` 覆盖 `I18n`
  → **持久化 locale 优先于 `-Duser.language`**。而该文件当时写着 `"locale":"zh_CN"`。
- **后果**：`run-test-mode -Duser.language=en -Duser.country=US`（会话 17 文档 §五 的做法）实际渲染的是**中文界面**，
  断言"30/30 通过"却完全没验证英文路径。
- **修正**：改为**运行前种入/删除** `gui-state.json` 的 locale（`.claude-work/seed-gui-state.js`），运行后恢复。
- **验证 locale 真的生效**（不采信计数器）：same-fixture en 运行的会话目录出现 `Group10.zip`（zh 为 `组…`），
  即 `core.groupDefault` 的 en 值 `Group` 确实被使用。
- **遗留（登记）**：GUI 自动化的 30 项断言是 locale 无关的**控制状态**断言，
  **不校验界面文案语言**。真正的"英文界面无中文残留"仍属 I2 人工点验范畴（阶段 D 遗留）。
  另有：应用**日志**文案（`log.info` 等）本来就不属于 UI 文案（会话 15 有意不动），英文运行下日志仍为中文，这是设计使然、非缺陷。

### 3. 行数口径陷阱（已写入架构测试注释）

`MainController.java` 实测 **6111** 行，但**不同工具数出的结果不同**：
PowerShell `(Get-Content f).Count` = **5882**，Node（按 Java 规则）= **6111**，Java `Files.readAllLines` = **6111**。
原因：文件为纯 `LF` 换行，`Get-Content` 的分行/编码处理与之不一致。
→ 架构测试的 `MAIN_CONTROLLER_MAX_LINES` **只能与 `Files.readAllLines` 口径比较**，
不要拿 PowerShell 的数字去改它（会立刻假失败或假通过）。
另：`docs/新会话交接总纲.md` 记的"约 6100 行"**是对的**，会话 18 早先汇报的 5882 是 PowerShell 口径的误读，此处更正。

### 4. 附带修正：架构白名单最初不完整（本测试自身抓出来的）

只凭 `grep 'import javafx'` 得出的泄漏点是 2 个，**实际是 4 个** ——
`DropResolver` 与 `OutputUnitPlanner` **没有** import javafx，而是在方法签名里用了**全限定名**
`javafx.collections.ObservableList`。
这正是"扫字节码而非扫 import"的价值：**源码 grep 会漏，常量池不会**。
（该发现同时说明会话 17 链路清单的耦合点 #2 覆盖面偏窄：`GroupStructure` 之外还有两个 util 类同样依赖 `ObservableList`。）
